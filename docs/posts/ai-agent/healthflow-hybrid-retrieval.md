# HealthFlow 的 RAG 召回：词法检索与语义检索如何协同工作

HealthFlow 的知识库问答采用 RAG（Retrieval-Augmented Generation）架构。模型回答用户问题前，系统会先从公共健康知识库和当前会话关联的个人文档中召回相关片段，再把这些片段作为上下文和证据交给大模型。

项目同时使用词法检索和语义检索：

- 词法检索关注查询词是否出现在文档中；
- 语义检索关注问题和文档表达的含义是否相近；
- 两路结果通过 RRF 融合；
- 最后可以使用 DashScope Rerank 模型进行重排。

## 一、整体检索流程

```text
用户问题
   │
   ├── 公共知识库：PostgreSQL 词法检索
   ├── 公共知识库：Embedding 语义检索
   └── 个人文档：词法候选 + 向量候选
            │
            ▼
      候选去重与 RRF 融合
            │
            ▼
      DashScope Rerank 重排
            │
            ▼
      返回 Top K 引用片段
```

入口位于 `apps/api/src/knowledge/rag.service.ts:79`。

系统不会只召回最终需要的几个片段，而是先扩大候选范围，候选数通常至少为 topK × 4，最多不超过 30 个，再进行后续融合和重排。

## 二、词法检索：根据文字匹配程度召回

### 1. 公共知识库的词法检索

公共知识库的词法检索在 PostgreSQL 内部完成，主要组合了以下信号：

- to_tsvector 和 plainto_tsquery：全文检索；
- ts_rank_cd：全文匹配相关性评分；
- pg_trgm 的 similarity() 和 %：字符级模糊匹配；
- keywords 数组匹配：判断关键词或标签是否命中；
- LIKE：补充查询扩展词的子串匹配。

综合评分大致为：

```text
score =
  2 × ts_rank_cd(全文匹配分)
  + similarity(正文, 查询)
  + 1.5 × similarity(标题, 查询)
  + 0.3 × 标签命中奖励
  + 1.4 × 查询扩展词命中比例
```

ts_rank_cd 是 PostgreSQL 的 Cover Density 排名函数，会考虑全文匹配信息以及匹配词的覆盖范围。它不是 BM25。

pg_trgm 会把文本拆成字符三元组，根据三元组重合程度计算相似度。例如，查询词和正文没有完全相同，但字符片段相近时，也可能被召回。

项目的数据库迁移还创建了 pg_trgm 扩展和正文的 GIN Trigram 索引，见：

`apps/api/prisma/migrations/20260629000000_add_rag_uploads/migration.sql:111`

### 2. 中文查询扩展

项目没有使用专门的中文全文分词器，而是对查询做了规则增强：

1. 提取英文、数字和汉字查询词；
2. 对中文提取 2～4 个汉字的连续片段；
3. 过滤“什么、怎么、建议”等常见疑问词；
4. 根据健康领域预设规则扩展相关表达。

例如：

```text
睡不着
→ 入睡困难、入睡潜伏期、睡前、夜醒

咖啡
→ 咖啡因、浓茶、能量饮料

焦虑
→ 惊恐、缓慢呼气、呼吸节奏、稳定
```

因此，当前公共词法检索并不是简单的字符串查询，而是：

```text
全文检索 + 字符相似度 + 关键词匹配 + 领域规则扩展
```

### 3. 个人文档的词法检索

个人文档首先会进行权限过滤：

- 文档属于当前用户；
- 文档状态为 published；
- 上传文件关联到当前会话。

然后 PostgreSQL 先筛选候选片段：

- 最多 3000 个向量模型相同的片段；
- 最多 500 个关键词或正文包含查询扩展词的片段。

候选结果去重后，由 API 端的 lexicalScore 计算词法分数。它会：

- 给查询词和中文片段赋权；
- 统计查询词命中权重；
- 计算扩展词命中情况；
- 对完整查询字符串命中增加奖励。

这部分是自定义规则评分，并不是 BM25。

对应代码：`apps/api/src/knowledge/rag.service.ts:721`。

## 三、语义检索：通过向量比较文本含义

### 1. 生成 Embedding

系统通过 `apps/api/src/knowledge/embedding.service.ts:20` 生成文本向量：

- 优先调用当前模型供应商的 Embedding API；
- 文本按批次处理；
- 返回结果归一化；
- 记录使用的模型名称。

如果供应商不支持 Embedding，或者远程调用失败，则使用本地回退模型 local-hash-embedding-v1。

本地回退方案会：

1. 提取英文、数字、汉字和二元字符片段；
2. 使用哈希函数映射到 384 维数组；
3. 对数组进行归一化；
4. 使用余弦相似度计算文本接近程度。

这种方案能够保证系统在没有外部 Embedding 服务时继续运行，但它更接近哈希化的词法特征，不等同于真正训练得到的语义模型。

### 2. 向量存储位置

个人文档在上传和分块时生成向量，保存到 PostgreSQL 的 KnowledgeChunk.embedding JSONB 字段：

```prisma
model KnowledgeChunk {
  id             String   @id @default(uuid())
  documentId     String
  content        String
  keywords       String[]
  embedding      Json?
  embeddingModel String?
}
```

相关模型定义见：

`apps/api/prisma/schema.prisma:266`

公共知识库的文本和元数据保存于 PostgreSQL，但公共片段向量会在需要时生成，并缓存到 API 进程内的 Map 中。这个缓存：

- 不写入数据库；
- 不跨 API 实例共享；
- API 重启后需要重新生成。

用户问题的向量只在当前请求中生成，不会持久化。

### 3. 余弦相似度计算

问题和文档片段分别转换成向量后，API 端计算余弦相似度：

```text
cosine(query, document) =
  query · document / (|query| × |document|)
```

相似度越高，说明两个向量的方向越接近。

当前项目没有使用 pgvector、Milvus 或 Qdrant，所以不是由向量数据库执行近邻搜索，而是：

```text
从 PostgreSQL 读取候选片段
→ 取出 JSONB 向量
→ 在 API 内存中逐个计算余弦相似度
→ 排序
```

### 4. 公共知识库的语义分数

公共语义召回的分数为：

```text
0.9 × 向量相似度 + 0.1 × 词法分数
```

公共知识库最多读取约 3000 个片段，逐个计算向量相似度后排序。

### 5. 个人文档的混合分数

个人文档根据 Embedding 来源调整权重：

```text
远程 Embedding：
0.85 × 向量分数 + 0.15 × 词法分数

本地哈希向量：
0.55 × 向量分数 + 0.45 × 词法分数
```

本地哈希向量的语义能力较弱，因此系统会降低它的权重，增加词法匹配的影响。

## 四、当前项目没有使用 BM25

当前项目的词法检索不是标准 BM25，而是 PostgreSQL 全文检索和规则增强评分。

BM25 通常会考虑：

- TF：词在文档中出现的频率；
- IDF：词在整个语料库中的稀有程度；
- 文档长度归一化：避免长文档天然占优。

典型形式可以简化为：

```text
BM25(D, Q) =
Σ IDF(term) ×
  [ TF × (k1 + 1) ] /
  [ TF + k1 × (1 - b + b × 文档长度 / 平均文档长度) ]
```

两者的区别如下：

| 对比项 | 当前项目 | BM25 |
| --- | --- | --- |
| 全文相关性 | ts_rank_cd | BM25 公式 |
| 模糊匹配 | pg_trgm similarity | 标准 BM25 不负责 |
| 查询扩展 | 健康领域手工规则 | 通常需要额外组件 |
| IDF | 未显式实现 | 核心组成部分 |
| 文档长度归一化 | 未实现 | 核心组成部分 |
| 中文处理 | simple 配置、字符片段和规则扩展 | 依赖中文分词 |

因此，更准确的说法是：

HealthFlow 使用 PostgreSQL 全文检索、Trigram 模糊匹配和自定义规则增强的词法召回，而不是 BM25 召回。

## 五、三路结果如何融合

词法分数和向量分数不在同一个数值尺度上，因此系统不直接把它们相加，而是使用 RRF（Reciprocal Rank Fusion）进行排名融合：

```text
fusionScore = Σ 路径权重 / (60 + 候选排名)
```

当前配置中：

- 公共词法结果权重为 1.08；
- 公共语义结果权重为 1；
- 个人文档结果权重为 1。

一个片段如果同时出现在多个召回路径中，并且排名靠前，就会得到更高的融合分。

融合过程还限制同一文档最多贡献两个片段，避免最终上下文全部来自同一篇文档。

个人文档如果某个片段分数较高，还会尝试加入它前后的相邻片段，以保持上下文连续性。

## 六、Rerank 是召回后的二次排序

RRF 融合后，候选片段可以交给 DashScope 的 gte-rerank-v2 进行重排。

Embedding 召回的过程是：

```text
问题 → 向量
文档 → 向量
向量之间计算相似度
```

Rerank 的过程则是：

```text
问题 + 候选片段
→ 由重排模型直接判断相关性
```

Rerank 通常比单纯的向量距离更精细，因为模型可以同时读取问题和候选文本。

如果 Rerank：

- 被关闭；
- 缺少 API Key；
- 调用失败；

系统就会回退到融合后的结果。

当前代码还有一个值得注意的细节：当 Rerank 没有应用时，回退集合主要由个人文档和公共词法结果组成，公共语义结果不会进入 fallbackCitations。因此，公共语义召回主要在 Rerank 成功时参与最终引用。

## 七、这套方案的优点

### 基础设施简单

项目只需要 PostgreSQL、Redis 和 API 服务，不需要额外部署向量数据库。

### 多种召回方式互补

- 词法检索适合明确关键词；
- 语义检索适合表达改写和同义问题；
- Trigram 适合模糊文本；
- 查询扩展适合固定健康领域；
- Rerank 负责最终精排。

### 支持降级

外部 Embedding 服务不可用时，可以回退到本地哈希向量；Rerank 不可用时，也可以回退到基础召回结果。

### 用户文档隔离清晰

个人文档检索同时检查用户、文档状态和会话关联，降低跨用户、跨会话召回的风险。

## 八、当前方案的限制

1. 没有向量索引，语义检索需要逐个计算，数据量增大后性能会下降；
2. 公共向量缓存只存在于单个 API 进程中，多实例部署会产生重复计算；
3. PostgreSQL 的 simple 配置不是完整的中文分词方案；
4. 本地哈希向量不能真正理解复杂的同义表达；
5. 词法检索没有标准 BM25 的 IDF 和文档长度归一化；
6. Embedding 模型切换后，旧片段不会自动重新生成向量；
7. Rerank 失败时，公共语义结果的回退参与度有限。

## 九、后续演进方向

如果知识库规模继续扩大，可以考虑：

1. 启用 PostgreSQL pgvector；
2. 将 JSONB 向量迁移到 vector 类型；
3. 建立 HNSW 或 IVFFlat 向量索引；
4. 为公共向量缓存增加持久化和跨实例共享；
5. 引入中文分词、同义词词典或专业搜索引擎；
6. 为 Embedding 增加版本号、批量重建和失败重试；
7. 记录每路召回的耗时、候选数、命中率和最终排名；
8. 将公共语义结果加入无 Rerank 时的回退融合。

## 结语

HealthFlow 的检索系统不是单纯的向量搜索，也不是标准 BM25 搜索，而是一个混合召回系统：

```text
PostgreSQL 全文和模糊检索
+ 自定义关键词评分
+ Embedding 语义检索
+ 余弦相似度
+ RRF 排名融合
+ DashScope Rerank 重排
```

PostgreSQL 负责保存业务数据、知识文档和部分向量；API 负责向量计算、混合评分和排序。这个方案减少了基础设施依赖，适合当前规模的健康知识库。随着数据量和并发量增长，向量索引、中文分词、共享缓存和标准化词法评分会成为后续优化重点。
