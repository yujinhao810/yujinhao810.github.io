# 从 Agent 到 SDD：如何让 AI 真正可靠地参与软件开发

## 一、为什么会用 AI 写代码，不代表会 AI 开发？

随着大语言模型的发展，AI 已经不再只是一个回答问题的聊天工具。借助工具调用、外部上下文、代码执行和任务规划，AI 可以参与需求分析、代码编写、测试、调试，甚至完成一整套开发流程。

但在实际开发中，我们经常会遇到以下问题：

- AI 写出来的代码看起来正确，运行后却出现异常。
- AI 不理解项目原有架构，重复创建已有组件或工具函数。
- 修改一个功能时，意外破坏了其他功能。
- AI 根据不完整的需求自行补充业务规则，最终实现与预期不符。
- 代码能够运行，但缺少异常处理、边界条件和必要的测试。

这些问题的根源，并不只是模型能力不足，而是**需求不明确、上下文不充分、执行过程缺少约束，以及验收机制不完善**。

要提高 AI 辅助开发的可靠性，需要理解 Agent、Function Calling、MCP 等技术的作用，并建立从需求定义到测试验收的完整开发流程。

## 二、Agent、Function Calling 与 MCP

### 2.1 什么是 Agent？

Agent（智能体）是一种能够围绕目标进行规划、调用工具、观察执行结果，并根据反馈继续行动的 AI 系统。

传统的聊天模型通常采用这样的流程：

用户提出问题 → 模型生成回答 → 结束。

而具备工具使用能力的 Agent，可以采用更加动态的流程：

用户提出目标 → 模型分析任务 → 调用工具 → 获取执行结果 → 判断是否需要继续执行 → 返回最终结果。

例如，开发者希望 AI 帮忙修复一个 Vue 项目的表格筛选问题。

Agent 可以执行以下步骤：

1. 阅读项目文件，找到表格组件和筛选逻辑。
2. 分析筛选条件、请求参数和数据更新流程。
3. 修改相关代码。
4. 运行测试或构建命令。
5. 根据错误信息继续修改。
6. 汇总修改内容和测试结果。

这里需要注意：**Agent 不等于某个特定模型，而是一种围绕目标组织模型、工具和执行流程的系统设计方式。**

一个完整的 Agent 系统通常包含以下部分：

- **LLM：** 理解任务、分析信息、生成计划和决定下一步行动。
- **Tools：** 提供读取文件、查询数据库、调用接口、执行命令等能力。
- **Orchestration：** 编排任务步骤、管理执行状态和控制流程。
- **Memory / Context：** 为模型提供当前任务所需的历史信息、项目知识和中间结果。
- **Feedback：** 根据工具执行结果、测试结果或用户反馈调整后续行为。

其中，Memory 并不一定是长期记忆，也可以只是当前任务的状态或历史执行记录。

Agent 的关键不只是能够调用工具，而是能够围绕目标，根据反馈决定接下来做什么。

### 2.2 什么是 Function Calling？

Function Calling，通常称为函数调用或工具调用，是让模型以结构化形式提出工具调用请求的一种机制。

传统情况下，模型只能输出文本。例如：

> 请帮我查询用户 ID 为 1001 的订单。

如果模型能够使用工具，它可以根据预先提供的函数定义，生成结构化的调用参数：

```json
{
  "name": "getOrder",
  "arguments": {
    "userId": 1001
  }
}
```

应用程序接收到调用请求后，执行真正的 `getOrder` 函数，并将执行结果返回给模型。

例如：

```javascript
async function getOrder(userId) {
  const response = await fetch(`/api/orders?userId=${userId}`);

  if (!response.ok) {
    throw new Error("订单查询失败");
  }

  return response.json();
}
```

需要注意，上面的 JSON 只是模型提出的调用请求。它本身并没有执行 HTTP 请求，也不意味着订单已经成功查询。

实际执行流程如下：

```text
用户提出问题
      ↓
模型判断需要调用工具
      ↓
模型生成函数名称和参数
      ↓
应用程序校验参数并执行函数
      ↓
函数返回执行结果
      ↓
模型根据结果继续分析或回答
```

Function Calling 主要解决两个问题：

1. **让模型以结构化方式表达调用意图。**
2. **让应用程序能够根据模型的调用请求执行真实操作。**

它并不意味着模型可以随意执行任何函数。开发者需要提前定义允许使用的工具，并由应用程序负责参数校验、权限控制、异常处理和实际执行。

例如，模型请求删除用户数据时，后端不能仅因为模型生成了合法的函数参数，就直接执行删除操作。

### 2.3 什么是 MCP？

MCP，全称 Model Context Protocol，即模型上下文协议，是一种用于 AI 应用与外部工具、数据源和上下文服务进行标准化交互的开放协议。

在没有统一协议的情况下，每个 AI 应用都可能需要单独开发不同的工具集成逻辑。

例如：

- AI 应用 A 使用自定义接口读取 GitHub 仓库。
- AI 应用 B 使用另一套接口查询数据库。
- AI 应用 C 使用不同的方式读取本地文件。

这会导致集成逻辑重复，工具难以跨应用复用。

MCP 通过定义统一的交互方式，帮助 AI 应用连接不同的外部服务。

MCP 常见的核心概念包括：

| 概念 | 作用 |
|---|---|
| MCP Host | 用户实际使用的 AI 应用，例如支持 MCP 的开发工具 |
| MCP Client | Host 内负责与 MCP Server 通信的组件 |
| MCP Server | 向客户端提供工具、资源或提示模板的服务端程序 |
| Tools | 可由模型请求调用、由应用或服务执行的操作 |
| Resources | 可供应用读取的上下文资源，例如文档或数据 |
| Prompts | 服务端提供的可复用提示模板 |

例如，可以开发一个 GitHub MCP Server，为 AI 提供查询仓库、读取 Issue、查看 Pull Request 等能力。

当用户要求 AI 分析某个仓库中的 Bug 时，AI 应用可以通过 MCP 获取相关信息，再结合模型的分析能力完成任务。

需要注意：MCP 服务器不一定是远程部署的 HTTP 服务，也可以通过本地进程等方式通信。具体连接方式取决于所采用的 MCP 传输机制。

### 2.4 Function Calling 与 MCP 有什么区别？

两者经常一起出现，但它们解决的问题不同。

| 比较维度 | Function Calling | MCP |
|---|---|---|
| 核心作用 | 让模型提出结构化的工具调用请求 | 标准化 AI 应用与外部能力之间的交互 |
| 主要关注点 | 调用意图和参数 | 工具、资源、提示模板及通信约定 |
| 是否负责执行 | 通常由宿主应用执行函数 | 通常由 MCP Client 与 Server 协作完成调用 |
| 是否可以单独使用 | 可以 | 可以，但需要支持 MCP 的客户端和服务端 |
| 典型用途 | 调用业务 API、查询订单、计算数据 | 连接 GitHub、文件系统、数据库等外部能力 |

可以把它们理解为不同层次的技术：

- Function Calling 解决模型如何表达工具调用意图的问题。
- MCP 解决 AI 应用如何以标准化方式连接外部能力的问题。
- Agent 则负责组织模型、工具和执行反馈，使系统能够围绕目标完成任务。

三者并不是互相替代的关系。

### 2.5 它们之间如何协同工作？

以一个使用 React、NestJS 开发的 AI 编程助手为例。

用户提出需求：

> 帮我检查当前项目中的 API 请求封装，并找出重复实现的请求逻辑。

系统可能采用以下流程：

1. Agent 分析任务，判断需要先了解项目结构。
2. 模型通过 Function Calling 请求调用文件搜索工具。
3. 应用程序执行搜索，并把结果返回模型。
4. 如果需要访问 GitHub 仓库或其他外部数据源，AI 应用也可以通过 MCP 获取相关上下文。
5. Agent 根据获取的信息，继续阅读代码、比较实现方式。
6. 模型提出修改建议，或请求调用编辑工具。
7. 系统执行测试，向模型反馈结果。
8. Agent 汇总发现的问题、修改内容和验证情况。

其中，Function Calling 是模型与工具交互的一种方式，MCP 是连接外部能力的一种协议，而 Agent 是把整个任务组织起来的执行机制。

并不是所有 Agent 都必须使用 MCP，也不是所有 Function Calling 都需要构建完整的 Agent。

## 三、如何正确向 AI 提出开发需求？

### 3.1 为什么一句话需求往往不够？

假设我们告诉 AI：

> 帮我写一个 Vue 3 的用户列表页面。

这个需求存在大量未明确的信息：

- 页面需要展示哪些字段？
- 是否支持分页？
- 搜索条件有哪些？
- 搜索是实时触发还是点击按钮后触发？
- 请求失败时如何处理？
- 是否需要复用现有的 API 封装？
- 是否已经存在统一的表格组件？
- 是否允许修改路由和全局状态？

如果这些信息没有明确，模型就需要自行推断。

推断不一定错误，但不同的推断可能产生完全不同的实现。因此，**高质量的 AI 开发需求不仅要描述想做什么，还要明确约束、预期行为和验收标准。**

### 3.2 一个有效的需求描述框架

向 AI 提出开发需求时，可以从以下几个方面进行描述。

**第一，任务目标。**

明确希望解决什么问题，而不是只描述需要修改哪些代码。

例如：

> 为用户管理页面增加按用户名和状态筛选的能力。

**第二，项目上下文。**

说明技术栈、项目结构和已有实现。

例如：

> 项目使用 Vue 3、Composition API、TypeScript 和 Element Plus。现有列表接口已经封装在 `src/api/user.ts` 中，请优先复用现有 API 和组件。

**第三，功能要求。**

明确每个功能的具体行为。

例如：

- 支持输入用户名进行筛选。
- 支持选择用户状态。
- 点击查询按钮后发送请求。
- 点击重置按钮后清空筛选条件，并恢复默认列表。
- 请求期间显示加载状态。

**第四，约束条件。**

明确不允许做什么。

例如：

- 不新增重复的 HTTP 请求封装。
- 不修改与本需求无关的文件。
- 不引入新的依赖。
- 保持现有 API 返回格式和组件使用方式不变。

**第五，验收标准。**

用可以观察、验证的结果描述完成条件。

例如：

- 输入用户名后点击查询，接口收到正确的用户名参数。
- 切换状态后查询，接口收到正确的状态参数。
- 点击重置后，表单字段恢复默认值，列表重新加载。
- 请求失败时显示错误提示。
- 现有分页功能仍然正常。

**第六，交付要求。**

明确希望 AI 提供什么。

例如：

> 请先分析现有实现，给出修改计划；确认后再修改代码。完成后说明修改的文件、核心逻辑、测试结果和仍未解决的问题。

### 3.3 一个可复用的 AI 开发提示词

下面的模板可以直接用于实际项目开发。

```text
你是一名熟悉当前项目技术栈的软件工程师。

一、任务目标
[描述需要实现的功能或需要解决的问题]

二、项目上下文
- 技术栈：[例如 Vue 3、TypeScript、Vite]
- 相关文件：[列出已知文件或目录]
- 已有实现：[说明现有 API、组件和业务逻辑]

三、功能要求
1. [功能要求一]
2. [功能要求二]
3. [功能要求三]

四、约束条件
1. 优先复用现有组件、工具函数和 API。
2. 不修改与需求无关的代码。
3. 不擅自引入新的依赖。
4. 不确定的业务规则必须先提出问题，不要自行假设。
5. 不得伪造接口返回、测试结果或执行成功状态。

五、验收标准
1. [可验证的预期行为]
2. [异常场景的预期行为]
3. [回归检查要求]

六、执行流程
1. 先阅读相关代码和项目规范。
2. 分析当前实现，列出需要修改的文件及原因。
3. 指出存在的不确定性和潜在风险。
4. 在确认方案后实施修改。
5. 运行适当的测试、类型检查或构建。
6. 根据真实执行结果修复问题。
7. 最后汇总修改内容、验证结果和未完成事项。

注意：如果缺少执行环境或测试条件，请明确说明，
不得把推测当作已经验证的事实。
```

这类提示词的核心价值并不是让提示词变得更长，而是减少模型必须自行猜测的信息。

### 3.4 为什么要让 AI 先分析，再编写代码？

对于复杂任务，建议将工作拆分为两个阶段。

第一阶段：分析。

要求 AI 阅读相关代码，说明现有实现、潜在问题、拟修改文件和实施方案。

第二阶段：执行。

确认方案后，再要求 AI 修改代码并运行验证。

这样做有几个好处：

- 可以及时发现 AI 对项目结构的错误理解。
- 可以在代码修改前纠正不合理的设计。
- 可以限制修改范围，减少无关重构。
- 可以降低 AI 直接生成大量代码、却没有理解现有逻辑的风险。

对于简单且明确的任务，可以直接执行；对于涉及多个模块、数据结构或公共接口的任务，先分析再实施通常更稳妥。

## 四、如何验收 AI 生成的代码？

AI 生成代码后，不能仅凭代码看起来合理就认定任务完成。

软件开发中的验收应该基于明确的需求和实际证据，而不是模型的自我评价。

### 4.1 第一层：需求验收

检查 AI 是否真正实现了要求的功能。

例如，需求要求：

> 点击重置后清空筛选条件，并重新加载默认列表。

就需要分别检查：

1. 输入框和下拉框是否恢复默认值。
2. 内部保存的筛选条件是否同步重置。
3. 是否重新发起列表请求。
4. 请求参数是否符合默认列表的约定。

如果只是清空了页面上的输入框，却没有重置实际请求参数，就不能算完整实现。

### 4.2 第二层：代码验收

检查实现是否符合项目的技术规范。

重点包括：

- 是否复用了现有 API、组件和工具函数。
- 是否存在重复逻辑或不必要的抽象。
- 是否正确处理异步操作。
- 是否存在空值、类型不匹配等问题。
- 是否存在资源泄漏或不必要的状态更新。
- 是否意外修改了其他模块。
- 是否引入了不必要的依赖。

例如，在 Vue 3 中，以下代码就可能存在问题：

```javascript
async function loadUsers() {
  loading.value = true;

  const result = await getUsers();

  users.value = result.data;
  loading.value = false;
}
```

如果 `getUsers()` 请求失败，`loading.value` 就可能一直保持为 `true`。

可以改为：

```javascript
async function loadUsers() {
  loading.value = true;

  try {
    const result = await getUsers();
    users.value = result.data;
  } catch (error) {
    console.error("用户列表加载失败", error);
    // 根据项目规范显示错误提示
  } finally {
    loading.value = false;
  }
}
```

不过，异常处理不能只为了消除报错。还需要根据项目要求决定是否显示提示、保留旧数据或提供重试能力。

### 4.3 第三层：测试验收

测试的作用是通过实际执行验证代码行为。

常见的验证方式包括：

| 验证方式 | 主要检查内容 |
|---|---|
| 单元测试 | 单个函数或组件逻辑是否符合预期 |
| 集成测试 | 多个模块或组件协作是否正常 |
| 类型检查 | TypeScript 类型是否存在错误 |
| Lint 检查 | 代码是否符合静态规范 |
| 构建检查 | 项目是否能够完成编译和打包 |
| 手动测试 | 实际页面交互是否符合需求 |
| 回归测试 | 修改是否破坏原有功能 |

并不是每个任务都必须执行全部测试，但应该根据修改范围选择适当的验证手段。

例如，只修改一个纯函数，可以优先运行相关单元测试；如果修改了路由、状态管理和公共 API，就需要更广泛的集成与回归检查。

### 4.4 第四层：异常和边界条件验收

AI 很容易只覆盖正常情况，因此还需要主动检查异常路径。

以用户列表为例，可以检查：

- 列表为空时是否正常展示。
- 接口返回 `null` 或缺少字段时是否发生异常。
- 请求超时或服务器返回错误时是否有反馈。
- 用户连续点击查询按钮时是否出现重复请求。
- 快速切换筛选条件时，旧请求是否覆盖了新结果。
- 组件卸载后，异步请求是否仍然尝试更新状态。

这些问题不一定会在正常演示中出现，但可能直接影响生产环境的稳定性。

### 4.5 验收不是让 AI 自己说“通过”

可以要求 AI 提供以下信息：

```text
1. 修改了哪些文件？
2. 每个文件为什么需要修改？
3. 哪些需求已经实现？
4. 执行了哪些测试命令？
5. 每条命令的真实执行结果是什么？
6. 哪些异常场景已经验证？
7. 哪些内容尚未验证？原因是什么？
8. 是否存在已知风险或兼容性问题？
```

这里需要特别注意：如果 AI 没有真正执行测试，就不能把“预计通过”当成“测试通过”。

**验收的核心原则是：每一个重要结论，都应该尽可能对应可观察的证据。**

## 五、如何发现 AI 写错了代码？

发现 AI 生成代码中的错误，需要结合静态分析、动态验证、逻辑审查和项目上下文进行判断。

### 5.1 不要只看代码是否能够运行

代码能够编译、页面能够打开，并不意味着业务逻辑正确。

例如：

```javascript
const total = price * quantity;
```

这段代码本身没有语法错误，但如果 `price` 是字符串、`quantity` 可能为空，或者业务要求的是含税总价，那么实现仍然可能不符合需求。

因此，需要分别检查：

- 语法是否正确。
- 类型是否合理。
- 业务规则是否正确。
- 边界条件是否覆盖。
- 实际运行结果是否符合预期。

### 5.2 检查 AI 是否误解了项目

AI 可能根据文件名、局部代码或常见开发模式推测项目结构，但推测不一定准确。

常见错误包括：

- 引用了项目中不存在的函数。
- 假设某个 API 返回的数据结构与实际不符。
- 重复创建已有的工具函数。
- 使用了项目并未安装的依赖。
- 忽略已有的状态管理或路由机制。
- 修改公共接口时没有检查调用方。

因此，AI 修改代码前，应该先让它检查真实文件和调用关系，而不是直接根据描述生成实现。

如果项目有多个相似模块，还应该要求它说明为什么选择当前文件，以及是否存在可复用的已有实现。

### 5.3 通过边界条件暴露隐藏错误

假设我们需要实现一个搜索功能。

正常测试可能只包含：

```text
输入：张三
结果：正确返回张三的记录
```

但还需要检查：

```text
输入为空
输入只有空格
没有匹配记录
接口返回空数组
接口返回异常数据
连续触发搜索
先发出的请求晚于后发出的请求返回
```

尤其是在前端开发中，异步竞态是一个典型问题。

例如，用户先搜索“张”，再迅速搜索“张三”。如果第一个请求最后才返回，就可能用旧结果覆盖新结果。

可以通过以下方式应对：

- 使用请求取消机制，例如 `AbortController`。
- 为请求分配递增的标识，只允许最新请求更新状态。
- 使用适当的请求库或数据管理机制处理竞态。

具体采用哪种方案，需要结合现有项目架构和请求复用情况决定。

### 5.4 让 AI 提出反例，而不是只证明自己正确

AI 在编写代码后，还可以被要求从审查者的角度检查实现。

例如：

```text
请暂时不要继续修改代码。

从严格的代码审查角度检查当前实现：
1. 找出可能违反需求的地方。
2. 检查空值、异常、并发和边界条件。
3. 检查是否引入重复实现或破坏现有接口。
4. 对每个问题指出具体代码位置和触发条件。
5. 区分已经确认的问题与尚未证实的风险。
6. 如果没有发现问题，也请说明检查范围和未覆盖的部分。
```

这种方法能够促使模型主动寻找反例，但仍然不能替代真实测试。

### 5.5 使用独立证据交叉验证

如果条件允许，可以让 AI 生成代码，再使用不同的验证方式检查结果：

- 代码生成：根据需求实现功能。
- 静态检查：通过 TypeScript、ESLint 等工具检查代码。
- 测试执行：通过单元测试和集成测试验证行为。
- 人工审查：检查业务规则、架构和潜在风险。

这些方法相互补充，可以减少单一检查方式的盲区。

不过，多个 AI 角色或多轮 AI 审查也可能共享相同的错误假设，因此不能简单地把多个模型的一致意见当作正确性证明。

## 六、如何防止 AI 重复造轮子？

重复造轮子是 AI 编程中比较常见的问题。

例如，项目中已经有统一的 Axios 请求封装，AI 却又创建一个新的请求实例；项目已经有日期格式化函数，AI 又写了一个功能相同的函数。

这通常是因为模型没有获得足够的项目上下文，或者需求没有明确复用约束。

可以从以下几个方面改善。

### 6.1 先搜索，再实现

在编写新代码之前，先搜索项目中的：

- 同名函数和相似函数。
- 已有组件。
- API 请求封装。
- 状态管理模块。
- 通用工具函数。
- 相关测试和文档。

如果项目支持文件搜索工具，可以让 AI 先检索相关文件，再根据实际实现做出判断。

### 6.2 建立项目规范

可以在项目中维护 `AGENTS.md`、开发文档或其他项目约定文件，记录：

- 项目技术栈和目录结构。
- 组件、API 和工具函数的复用规则。
- 代码风格和命名规范。
- 测试命令和构建命令。
- 依赖管理方式。
- 禁止随意修改的公共模块。

具体使用哪种规范文件，取决于开发工具是否支持以及团队的实际约定。

关键是让 AI 在开始任务时能够读取这些规范，而不是假设它天然了解整个项目。

### 6.3 通过约束减少不必要的修改

可以明确要求：

> 修改前先搜索现有实现。只有在确认现有代码不能满足需求时，才新增函数或组件。若需要新增，请说明现有实现为什么不能复用。

此外，还可以要求 AI 输出修改文件清单，并限制本次任务的修改范围。

如果任务需要大范围重构，应当单独规划，而不是把无关重构混入一个小功能需求中。

## 七、什么是 SDD：规范驱动开发？

### 7.1 SDD 的核心思想

SDD 通常指 Specification-Driven Development，即规范驱动开发。

它强调在实现代码之前，先明确并维护一份可供开发、测试和验收共同使用的规范。

传统的开发流程有时是：

```text
需求描述 → 编写代码 → 测试 → 修复问题
```

采用 SDD 思路后，可以组织为：

```text
需求定义
   ↓
编写功能规范
   ↓
明确技术方案和约束
   ↓
拆分实现任务
   ↓
编写代码与测试
   ↓
根据规范验收
```

其核心不是增加文档数量，而是让需求、实现和验收具有明确的对应关系。

尤其是在 AI 编程中，规范可以减少模型自行补充业务规则的空间，也能为后续的代码修改和测试提供依据。

需要说明的是，SDD 在不同团队和工具中可能有不同的具体流程。有些强调先写规格，有些还会维护设计文档、任务清单和持续更新的规范文件，但共同点都是让明确的规范成为开发过程中的重要依据。

### 7.2 规范应该包含什么？

以“用户管理页面增加状态筛选功能”为例。

一份可执行的功能规范可以包括以下内容。

**需求背景**

用户管理页面目前只能按用户名查询，需要增加状态筛选，以便快速定位不同状态的用户。

**功能要求**

1. 用户可以选择全部、启用、禁用三种筛选状态。
2. 点击查询按钮后，根据当前筛选条件发送请求。
3. 点击重置按钮后，恢复默认筛选条件并重新加载列表。
4. 请求期间展示加载状态。
5. 请求失败时展示错误信息。

**业务规则**

- “全部”对应的请求参数由现有 API 约定决定，不能擅自假设是 `null`、空字符串还是不传参数。
- 查询条件应与分页行为保持一致。
- 新查询发起后，旧请求不得覆盖新查询的结果。

**技术约束**

- 使用现有 Vue 3 和 Element Plus 组件。
- 复用现有用户列表 API。
- 不新增重复的请求封装。
- 保持现有列表数据结构不变。

**验收标准**

- 选择启用后查询，接口参数与规范一致。
- 选择禁用后查询，接口参数与规范一致。
- 重置后，筛选条件和列表数据均恢复预期状态。
- 接口失败时，加载状态可以正确结束。
- 快速切换筛选条件时，不出现旧结果覆盖新结果的情况。

这份规范可以直接指导开发和测试，不只是对需求的简单复述。

### 7.3 SDD 与传统提示词有什么区别？

普通提示词主要告诉模型本次需要完成什么任务。

SDD 则强调把需求和规则沉淀为相对稳定、可检查的规范，并在后续实现和验收中持续使用。

| 比较维度 | 普通提示词开发 | SDD 思路 |
|---|---|---|
| 需求表达 | 可能主要依赖自然语言描述 | 维护结构化、可检查的功能规范 |
| 任务规划 | 可能直接开始编写代码 | 先明确需求，再规划实现任务 |
| 实现依据 | 当前对话及模型理解 | 需求规范、项目约束和现有代码 |
| 测试方式 | 可能依赖临时测试 | 根据规范中的验收标准设计测试 |
| 需求变更 | 容易只修改代码，遗漏相关行为 | 同步检查规范、实现和测试 |
| 适用场景 | 简单、低风险、一次性任务 | 复杂、长期维护或多人协作的项目 |

SDD 并不意味着所有简单需求都必须先编写长篇文档。

对于修改一个按钮文案这样的任务，直接说明目标并进行验证即可。对于涉及多个模块、业务规则、权限控制或公共接口的任务，先建立明确规范通常更有价值。

### 7.4 SDD 与测试驱动开发有什么区别？

SDD 和 TDD 经常一起使用，但它们关注的重点不同。

- **SDD（规范驱动开发）：** 重点是明确系统应该满足什么要求。
- **TDD（测试驱动开发）：** 重点是先编写能够表达预期行为的测试，再编写实现代码使测试通过。

两者可以结合：

1. 先通过 SDD 明确业务规则。
2. 根据验收标准编写测试。
3. 先运行测试，确认当前实现不能满足新要求。
4. 编写代码使测试通过。
5. 运行回归测试，检查原有功能是否受到影响。

对于 AI 辅助开发，这种方式能够让模型同时受到规范和测试结果的约束。

### 7.5 SDD 如何融入日常 AI 开发？

对于使用 React、NestJS 或 Vue 3 开发的项目，可以采用轻量级的规范驱动流程。

例如：

```text
项目规范
  ├── AGENTS.md
  └── 代码风格、目录结构、测试约定

功能需求
  ├── requirements.md
  ├── design.md
  └── tasks.md

具体实现
  ├── 前端组件
  ├── 后端接口
  └── 自动化测试
```

这只是一个示例目录，并不是 SDD 唯一规定的文件结构。

各文件的作用可以理解为：

- `AGENTS.md`：描述 AI 开发工具需要遵循的项目级约定。
- `requirements.md`：记录功能需求、业务规则和验收标准。
- `design.md`：说明必要的技术方案、接口设计和模块关系。
- `tasks.md`：将实现过程拆分为可执行、可检查的任务。

小型功能可以把这些内容合并到一个文档中，不必为了形式而拆分多个文件。

当需求发生变化时，应当先更新对应规范，再检查相关实现和测试是否需要同步调整。

## 八、把这些知识点串联起来：一套完整的 AI 开发工作流

理解了上述概念后，可以将它们整合为一套实际可执行的流程。

### 第一步：明确需求

不要急于让 AI 直接生成代码。

先说明任务目标、项目背景、功能要求、约束条件和验收标准。

对于不明确的业务规则，让 AI 先提出问题，而不是自行假设。

### 第二步：让 AI 了解项目

通过代码阅读、文件搜索和文档检索，了解已有实现。

如果 AI 开发工具支持 MCP，可以使用合适的 MCP Server 获取外部仓库、文档或其他上下文。

但需要注意，MCP 并不是读取项目代码的必要条件。本地文件工具、命令行工具或 IDE 内置能力同样可以提供相关上下文。

### 第三步：形成规范和实施计划

对于复杂任务，先形成需求规范、技术方案和任务清单。

要求 AI 说明：

- 当前实现是什么。
- 需要修改哪些文件。
- 为什么需要修改。
- 是否涉及公共接口。
- 可能有哪些风险。
- 如何验证每项需求。

确认方案后，再进入实现阶段。

### 第四步：执行代码修改

Agent 可以根据任务计划逐步读取文件、调用工具、修改代码和执行命令。

在这个过程中，Function Calling 可以作为模型请求调用工具的机制；MCP 可以作为连接外部工具和上下文服务的标准协议。

无论使用哪种方式，工具执行权限都应该受到约束。

例如，读取文件、修改代码、执行测试和删除文件的风险并不相同。对具有破坏性或涉及敏感数据的操作，应采用适当的权限控制和确认机制。

### 第五步：运行验证

根据规范中的验收标准选择验证方式。

例如：

```bash
npm run lint
npm run typecheck
npm run test
npm run build
```

以上只是示例命令，实际执行前应确认项目的 `package.json` 中存在对应脚本。

如果测试失败，应根据真实错误信息定位问题，而不是让 AI 在没有证据的情况下不断猜测修改方向。

### 第六步：审查修改结果

通过 Git diff 等方式检查实际变更：

```bash
git diff --check
git diff
```

重点检查：

- 修改是否超出需求范围。
- 是否删除或覆盖了已有逻辑。
- 是否引入不必要的依赖。
- 是否出现硬编码、重复代码或不合理抽象。
- 是否存在敏感信息泄露。
- 是否遗漏了异常处理和测试。

`git diff --check` 可以检查部分空白字符问题，但不能代替完整的代码审查。

### 第七步：按规范验收并交付

逐条对照验收标准，记录哪些项目已经通过、哪些没有通过、哪些尚未验证。

最终交付不应该只是源代码，还应该包括必要的修改说明、测试证据和已知限制。

整个流程可以概括为：

**需求 → 规范 → 计划 → 实现 → 验证 → 审查 → 验收。**

## 九、最后总结

AI 辅助开发的核心，不是让模型一次性写出尽可能多的代码，而是建立一套能够约束、验证和持续改进代码质量的工作方式。

可以从以下几个方面理解这些知识点：

1. **Agent：** 负责围绕目标组织推理、工具调用和执行反馈。
2. **Function Calling：** 让模型以结构化形式提出工具调用请求，由应用程序负责实际执行。
3. **MCP：** 标准化 AI 应用与外部工具、资源和上下文服务之间的交互。
4. **需求工程：** 将模糊的自然语言转化为明确的功能要求、约束和验收标准。
5. **代码验收：** 通过需求对照、代码审查、测试执行和边界条件验证确认实现质量。
6. **错误排查：** 结合真实项目上下文、静态分析、运行结果和独立证据发现问题。
7. **SDD：** 让明确的规范贯穿需求分析、代码实现、测试和后续维护。

对于前端开发者而言，尤其需要注意：AI 能够快速生成 Vue 或 React 组件，并不意味着它真正理解业务逻辑、请求时序、状态管理和项目架构。

真正有价值的能力，是能够准确描述需求、识别错误实现、验证代码行为，并让 AI 的工作过程符合工程规范。

**AI 可以帮助开发者提高编码效率，但需求是否正确、设计是否合理、结果是否可靠，仍然需要通过工程化的方法来保证。**
