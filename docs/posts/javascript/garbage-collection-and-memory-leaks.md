# JavaScript 垃圾回收与内存泄漏详解

## 一、什么是垃圾回收？

JavaScript 中的对象、数组、函数等数据在运行时需要占用内存。当这些数据不再被程序需要时，JavaScript 引擎会通过垃圾回收机制（Garbage Collection，简称 GC）回收相应的内存。

例如：

```js
let obj = {
    name: '小明',
    age: 20
};

obj = null;
```

执行 `obj = null` 后，变量 `obj` 不再引用原来的对象。如果没有其他可达引用指向该对象，那么该对象就有机会被垃圾回收。

需要注意：**将变量赋值为 `null` 并不意味着内存立即释放，而是解除该变量与原对象之间的引用关系。** 对象是否可以被回收，还取决于其他引用以及垃圾回收器的执行时机。

## 二、垃圾回收的主要方式

经典的垃圾回收算法主要有标记清除和引用计数。现代 JavaScript 引擎主要采用基于可达性分析的垃圾回收机制，并结合分代回收、增量回收等优化策略。

### 1. 标记清除（Mark-and-Sweep）

标记清除是现代 JavaScript 引擎常用的垃圾回收核心思路。

它的核心是判断对象是否仍然能够从 GC 根（GC Roots）访问到，而不是简单地判断变量是否离开作用域。

主要过程如下：

1. **标记阶段：** 从全局对象、当前执行栈中的活动引用等 GC 根出发，遍历引用关系，将可达对象标记为存活。
2. **清除阶段：** 没有被标记的对象，说明从 GC 根出发无法访问到，可以被回收。
3. **内存回收：** 回收不可达对象占用的内存。具体引擎还可能进行内存整理、压缩等操作。

示例：

```js
let obj1 = { name: '小明' };
let obj2 = { name: '小红' };

obj1 = null;
```

`obj1` 不再引用原对象。如果原对象没有其他可达引用，就可以被回收；`obj2` 引用的对象仍然可达，因此不能被回收。

标记清除还有一个重要优势：**能够处理循环引用。**

```js
function fun() {
    let obj1 = {};
    let obj2 = {};

    obj1.a = obj2;
    obj2.a = obj1;
}

fun();
```

虽然 `obj1` 和 `obj2` 相互引用，但函数执行结束后，如果两个对象都无法从 GC 根访问到，垃圾回收器仍然可以回收它们。

### 2. 引用计数（Reference Counting）

引用计数通过跟踪对象被引用的情况，判断对象是否仍然被使用。

例如：

```js
let obj = { name: '小明' };
let other = obj;

obj = null;
```

此时，虽然 `obj` 不再引用对象，但 `other` 仍然引用它，因此对象不能被回收。

继续执行：

```js
other = null;
```

如果不存在其他可达引用，该对象就可以被回收。

引用计数的主要问题是循环引用。

```js
function fun() {
    let obj1 = {};
    let obj2 = {};

    obj1.a = obj2;
    obj2.a = obj1;
}

fun();
```

两个对象相互引用，即使外部已经无法访问它们，彼此之间的引用仍然存在。传统的纯引用计数算法可能因此无法回收它们。

不过，现代 JavaScript 引擎主要依靠可达性分析等机制，因此循环引用本身并不意味着一定发生内存泄漏。

### 3. 两种方式对比

| 对比项           | 标记清除         | 引用计数        |
| ------------- | ------------ | ----------- |
| 判断依据          | 对象是否从 GC 根可达 | 对象的引用计数     |
| 循环引用          | 能处理不可达的循环引用  | 传统算法存在问题    |
| 主要特点          | 遍历可达对象       | 跟踪引用变化      |
| 现代 JavaScript | 常用的核心思路      | 不作为主要垃圾回收机制 |

## 三、如何减少不必要的内存占用？

垃圾回收是 JavaScript 引擎的正常机制，开发者并不需要刻意避免所有垃圾回收。真正需要关注的是不必要的对象创建、长期存活的无用引用，以及频繁的内存分配带来的性能开销。

### 1. 合理清空数组

清空数组常见的方式有两种。

方式一：将数组长度设置为零。

```js
let arr = [1, 2, 3];
let other = arr;

arr.length = 0;

console.log(arr);   // []
console.log(other); // []
```

`arr.length = 0` 会直接清空当前数组对象。由于 `arr` 和 `other` 引用的是同一个数组，所以两者都会看到空数组。

方式二：重新赋值为空数组。

```js
let arr = [1, 2, 3];
let other = arr;

arr = [];

console.log(arr);   // []
console.log(other); // [1, 2, 3]
```

`arr = []` 会创建一个新的空数组，并让 `arr` 引用它。原数组仍然被 `other` 引用，因此没有被清空。

两种方式的区别在于：

* `arr.length = 0`：修改原数组对象。
* `arr = []`：改变变量 `arr` 的引用。

如果其他模块也引用了该数组，选择哪种方式会影响这些模块看到的数据。

### 2. 及时解除不再需要的对象引用

```js
let user = {
    name: '小明',
    age: 20
};

user = null;
```

当对象不再需要时，可以解除不必要的引用。如果对象没有其他可达引用，就有机会被垃圾回收。

但不需要为了每个局部变量都手动赋值 `null`。当函数执行结束，局部变量不再可达时，相关对象通常就可以由垃圾回收器处理。

### 3. 避免不必要的函数创建

如果一个函数在循环中被反复创建，而且逻辑不依赖每次循环的局部状态，可以将函数定义移到循环外。

```js
const nums = [1, 2, 3, 4];

function format(value) {
    return `数字：${value}`;
}

nums.forEach(num => {
    console.log(format(num));
});
```

这样可以避免每次循环都创建一个新的 `format` 函数。

不过，函数创建不一定就是性能问题，现代引擎也会进行优化。应当结合代码实际情况判断，不要为了减少创建而牺牲可读性。

### 4. 合理管理缓存

缓存能够减少重复计算和请求，但如果缓存持续增长而不淘汰旧数据，也会占用越来越多的内存。

```js
const cache = new Map();

function saveData(key, value) {
    cache.set(key, value);
}
```

如果不断向 `cache` 添加数据，又从不删除，就可能造成内存占用持续增长。

实际项目中，可以采用容量限制、过期淘汰、LRU 等策略控制缓存规模。

## 四、哪些情况会导致内存泄漏？

内存泄漏是指程序不再需要某些数据，但由于引用关系或资源管理问题，这些数据仍然无法被回收，导致内存占用持续增加或长期保持在较高水平。

### 1. 意外的全局变量

在非严格模式下，给未声明的变量赋值可能意外创建全局变量，使其引用的数据长期存活。

```js
function fun() {
    // 非严格模式下可能创建全局变量
    leakedData = new Array(1000000).fill('data');
}

fun();
```

由于 `leakedData` 可能成为全局对象的属性，数组会一直保持可达。

解决方法是明确声明变量，并使用严格模式或 ES 模块。

```js
'use strict';

function fun() {
    const data = new Array(1000000).fill('data');
}
```

这里的 `data` 是局部变量，函数执行结束后，如果没有其他可达引用，数组就可以被回收。

### 2. 被遗忘的定时器或回调函数

定时器没有及时清理，可能使回调函数以及回调引用的数据一直存活。

```js
function start() {
    const data = new Array(1000000).fill('data');

    const timer = setInterval(() => {
        console.log(data.length);
    }, 1000);

    return () => clearInterval(timer);
}

const stop = start();

// 不再需要时，清理定时器
stop();
```

在这个例子中，定时器回调引用了 `data`。只要定时器仍然运行，这个引用就可能使数组持续存活。

实际开发中，需要在适当时机清理定时器、事件监听器和订阅。

### 3. 脱离 DOM 的引用

DOM 节点从页面移除后，如果 JavaScript 仍然保留对它的引用，该节点就可能继续占用内存。

```js
const button = document.querySelector('button');

const cache = {
    element: button
};

button.remove();
```

虽然按钮已经从页面中移除，但 `cache.element` 仍然引用它。

如果不再需要该节点，可以解除缓存引用：

```js
cache.element = null;
```

还要注意事件监听器的清理：

```js
function handleClick() {
    console.log('clicked');
}

button.addEventListener('click', handleClick);

// 不再需要监听时
button.removeEventListener('click', handleClick);
```

移除 DOM 节点本身，并不一定会自动解除所有 JavaScript 引用。

### 4. 不合理使用闭包

闭包可以让函数访问其词法作用域中的变量，是 JavaScript 的正常特性。闭包本身并不等于内存泄漏。

当一个长期存活的闭包引用了大量不再需要的数据时，才可能导致内存占用问题。

```js
function createHandler() {
    const largeData = new Array(1000000).fill('data');

    return function() {
        console.log(largeData.length);
    };
}

let handler = createHandler();

handler(); // 1000000

// 不再需要该闭包时
handler = null;
```

只要 `handler` 仍然引用闭包函数，函数所需要的 `largeData` 就可能继续存活。

当闭包函数不再被引用，并且没有其他可达引用保留相关数据时，这些数据才有机会被回收。

### 5. 无界缓存和未清理的订阅

实际项目中还应注意：

* **无界缓存：** 持续向 `Map`、对象或数组添加数据，却从不淘汰。
* **事件监听器未清理：** 重复注册监听器，旧回调及其引用的数据持续存活。
* **订阅未取消：** WebSocket、事件总线、观察者或流式任务仍然持有回调。
* **长生命周期任务：** 请求或异步任务长期引用不再需要的数据。

这些问题的共同点是：程序不再需要某些数据，但仍然保留了让数据可达的引用。

## 五、如何排查内存泄漏？

当页面运行时间越长、内存占用越高时，可以使用浏览器开发者工具进行排查。

以 Chrome DevTools 为例：

1. 打开开发者工具，进入 **Memory** 面板。
2. 使用 Heap snapshot（堆快照）记录当前内存中的对象。
3. 执行可疑操作，例如反复打开和关闭弹窗、切换路由或创建组件。
4. 再次拍摄堆快照，比较对象数量和内存占用。
5. 检查持续存活的对象及其 Retainers（保留引用链），定位是谁仍然引用它们。

判断内存泄漏时，不应仅凭一次内存占用较高就下结论。JavaScript 引擎可能延迟回收，也可能暂时保留已申请的内存。更重要的是观察重复操作后，内存和对象数量是否持续增长，以及这些对象为什么仍然可达。

## 六、面试总结

JavaScript 的垃圾回收主要基于可达性分析。标记清除从 GC 根出发，标记可达对象并回收不可达对象，因此能够处理循环引用；传统引用计数算法则可能因为循环引用而无法回收对象。

减少内存问题的关键不是强行减少垃圾回收次数，而是避免无用对象长期存活。例如，合理管理数组和缓存、及时清理定时器和事件监听器、解除不再需要的引用，并避免长期存活的闭包持有大量数据。

常见内存泄漏场景包括意外的全局变量、未清理的定时器或回调函数、脱离 DOM 的引用、不合理使用闭包，以及无界缓存和未取消的订阅。

**核心原则：对象不再使用，并不意味着它一定会被回收；只有当对象不再被任何可达引用所需要时，垃圾回收器才有机会回收它。**
