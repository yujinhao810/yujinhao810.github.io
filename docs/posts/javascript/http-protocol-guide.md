# HTTP 协议详解：从基础知识到面试高频考点

## 一、HTTP 协议基础

### 1. 什么是 HTTP 协议？

HTTP（HyperText Transfer Protocol，超文本传输协议）是一种应用层协议，主要用于客户端与服务器之间传输数据，采用经典的请求-响应通信模型。

在 Web 开发中，浏览器通常作为客户端，向服务器发送 HTTP 请求，服务器处理请求后返回 HTTP 响应。

HTTP 的主要特点：

- **简单灵活**：通过请求方法、请求头、状态码等机制描述通信行为。
- **可扩展**：可以通过请求头和响应头扩展协议能力。
- **无状态**：协议本身不自动保存不同请求之间的业务状态，可以借助 Cookie、Session、Token 等机制维护用户状态。
- **支持多种数据类型**：通过 `Content-Type` 描述传输内容的媒体类型。
- **可以使用不同版本的传输机制**：HTTP/1.1 和 HTTP/2 通常运行在 TCP 之上，HTTP/3 则运行在 QUIC 之上。

需要注意：HTTP 的无状态不等于服务器不能保存用户信息；HTTP/1.1 的持久连接也不代表 HTTP 协议本身有状态。

### 2. URL 的组成部分

URL（Uniform Resource Locator，统一资源定位符）用于定位网络资源。

例如：

```text
https://www.example.com:8080/news/index.html?type=tech&page=1#content
```

主要组成部分如下：

| 组成部分 | 示例 | 说明 |
|---|---|---|
| 协议 | `https` | 指定使用的协议 |
| 主机名 | `www.example.com` | 标识目标主机 |
| 端口 | `8080` | 标识目标服务端口 |
| 路径 | `/news/index.html` | 标识资源路径 |
| 查询参数 | `type=tech&page=1` | 向服务器传递查询条件 |
| 片段标识符 | `content` | 通常用于定位页面中的特定位置 |

其中，端口、路径、查询参数和片段标识符是否出现，取决于具体 URL。

默认情况下，HTTP 使用端口 80，HTTPS 使用端口 443。URL 中的片段标识符以 `#` 开始，通常由浏览器处理，不会作为 HTTP 请求目标的一部分发送给服务器。

### 3. 端口号的作用

一台主机可以运行多个网络服务。IP 地址主要用于定位主机，而端口号用于区分主机上的不同网络服务。

例如：

- `192.168.1.10:80`：可能对应 HTTP 服务。
- `192.168.1.10:443`：可能对应 HTTPS 服务。
- `192.168.1.10:3000`：可能对应开发环境中的 Web 服务。

因此，网络通信中通常使用 IP 地址和端口号共同定位目标服务。

## 二、HTTP 请求与响应

### 4. HTTP 请求报文的结构

HTTP/1.1 请求报文可以按照以下结构理解：

```http
POST /api/users HTTP/1.1
Host: example.com
Content-Type: application/json
Accept: application/json
Authorization: Bearer <token>

{"name":"Alice","age":20}
```

请求报文主要包含四个部分：

1. **请求行**：请求方法、请求目标和 HTTP 版本。
2. **请求头**：描述客户端、请求内容和通信条件等信息。
3. **空行**：分隔请求头和请求体。
4. **请求体**：可选，用于携带提交的数据。

请求体并不是 POST、PUT 等方法的专属。GET 请求在协议层面也可以携带内容，但其语义和中间设施兼容性存在限制，实际开发中通常不这样使用。

### 5. HTTP 响应报文的结构

例如：

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-cache

{"id":1,"name":"Alice"}
```

HTTP/1.1 响应报文主要包含四个部分：

1. **状态行**：HTTP 版本、状态码和原因短语。
2. **响应头**：描述响应内容、缓存策略、服务器行为等信息。
3. **空行**：分隔响应头和响应体。
4. **响应体**：服务器返回的数据。

需要注意，HTTP/2 和 HTTP/3 不再采用 HTTP/1.1 这种直接以文本行表达报文的线格式，但请求、响应、头部和数据等概念仍然存在。

### 6. 常见 HTTP 请求头和响应头

#### 常见请求头

| 请求头 | 作用 |
|---|---|
| `Host` | 指定请求的目标主机，HTTP/1.1 中通常要求提供 |
| `Accept` | 表示客户端能够接受的媒体类型 |
| `Accept-Language` | 表示客户端偏好的语言 |
| `Accept-Encoding` | 表示客户端支持的内容编码，如 gzip、br |
| `Content-Type` | 描述请求体的媒体类型 |
| `Authorization` | 携带身份认证凭据 |
| `Cookie` | 向服务器发送符合条件的 Cookie |
| `User-Agent` | 描述发起请求的客户端软件 |
| `Referer` | 提供引发当前请求的来源页面信息，可能受隐私策略限制 |
| `Cache-Control` | 表达请求侧的缓存要求 |
| `If-None-Match` | 携带实体标签，用于条件请求 |
| `Origin` | 表示请求的来源，用于 CORS 等场景 |

#### 常见响应头

| 响应头 | 作用 |
|---|---|
| `Date` | 表示消息生成的日期和时间 |
| `Server` | 描述服务器软件信息，可能被省略 |
| `Content-Type` | 描述响应体的媒体类型 |
| `Content-Length` | 在适用的消息格式中描述消息内容长度 |
| `Cache-Control` | 指定缓存策略 |
| `Expires` | 指定资源过期时间 |
| `ETag` | 提供资源的实体标签，用于验证资源版本 |
| `Last-Modified` | 表示资源最后修改时间 |
| `Location` | 常用于重定向或指示新建资源的位置 |
| `Set-Cookie` | 指示浏览器设置 Cookie |
| `Access-Control-Allow-Origin` | 指定允许跨域访问的来源 |

### 7. Content-Type 有哪些常见类型？

`Content-Type` 用于描述消息体的媒体类型。前后端联调时，需要确保客户端发送的数据格式与服务器预期一致。

#### application/x-www-form-urlencoded

常见于普通 HTML 表单提交。

```http
Content-Type: application/x-www-form-urlencoded

username=alice&age=20
```

字段通常采用 `key=value` 的形式，并通过 `&` 连接，相关字符会按照表单编码规则进行转义。

#### multipart/form-data

常用于表单上传文件。

```javascript
const formData = new FormData();

formData.append('username', 'alice');
formData.append('avatar', file);

await fetch('/api/upload', {
  method: 'POST',
  body: formData
});
```

使用浏览器的 `FormData` 上传时，通常不要手动设置 `Content-Type: multipart/form-data`，浏览器需要自动生成包含 boundary 的请求头。

#### application/json

常用于前后端 JSON 数据交互。

```javascript
await fetch('/api/users', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({
    name: 'Alice',
    age: 20
  })
});
```

#### text/xml 或 application/xml

用于传输 XML 格式的数据。具体使用哪种类型，取决于接口约定。

## 三、HTTP 请求方法

### 8. GET 和 POST 的区别

GET 和 POST 都是 HTTP 请求方法，但它们的语义不同。

| 对比维度 | GET | POST |
|---|---|---|
| 主要语义 | 获取资源的表示 | 根据资源自身的语义处理请求内容 |
| 安全性（HTTP 定义） | 安全方法 | 非安全方法 |
| 幂等性（HTTP 定义） | 幂等 | 不保证幂等 |
| 参数位置 | 查询参数常放在 URL 中 | 数据常放在请求体中 |
| 缓存 | 可以缓存，具体取决于缓存规则 | 通常不会被缓存，但协议并非绝对禁止 |
| 数据类型 | 可以发送请求内容，但通常不这样做 | 常用于提交 JSON、表单、文件等数据 |
| 长度限制 | 受浏览器、服务器、代理等实现限制 | 请求体也受服务器配置、网关及业务限制 |

#### GET 为什么通常是幂等的？

幂等是指：对同一资源重复执行相同请求，预期的服务器效果与执行一次相同。

例如：

```http
GET /api/users/1
```

重复请求用户信息，不应因为查询行为本身而重复创建或删除数据。

#### POST 为什么通常不保证幂等？

例如：

```http
POST /api/orders
Content-Type: application/json

{"productId":1001}
```

如果每次请求都会创建一个新订单，那么重复请求可能产生多个订单。

但实际业务可以通过幂等键、数据库唯一约束、事务等方式实现防重复提交。

#### GET 的参数为什么不适合传递敏感数据？

URL 可能出现在浏览器历史记录、服务器日志、代理日志、监控系统和引用来源等位置。因此，不应将密码、访问令牌等敏感数据直接放入查询参数。

不过，不能简单地说 POST 天然安全。**HTTPS 才是保护传输过程中数据机密性的重要机制**，服务器日志、请求体记录和应用程序本身仍需做好安全处理。

#### GET 的长度是否有固定限制？

HTTP 规范没有为 GET URL 规定统一的最大长度。实际限制由浏览器、服务器、代理和网关等共同决定。

因此，不应把某个浏览器的历史长度限制当作所有浏览器的通用标准。

### 9. POST 和 PUT 的区别

POST 与 PUT 的关键区别是请求语义，而不是简单地将它们等同于“新增”和“修改”。

- **POST**：请求目标资源按照自身语义处理请求内容。常用于创建资源、提交表单或触发业务操作。
- **PUT**：请求创建或替换目标资源的当前表示，具体效果取决于目标资源和服务器实现。对同一目标重复执行相同 PUT 请求，预期效果应保持一致。

例如：

```http
POST /api/users
Content-Type: application/json

{"name":"Alice"}
```

可能由服务器创建一个新用户，并分配用户 ID。

```http
PUT /api/users/1001
Content-Type: application/json

{"id":1001,"name":"Alice"}
```

可能用于创建或完整替换 ID 为 1001 的资源表示。

注意：PUT 并不必然意味着“只能修改已有数据”，它也可以用于创建资源；POST 也并非只能新增数据。

### 10. 常见 HTTP 请求方法

| 方法 | 主要用途 | 安全 | 幂等 |
|---|---|---|---|
| GET | 获取资源表示 | 是 | 是 |
| HEAD | 获取与 GET 类似的响应头，不返回响应体 | 是 | 是 |
| POST | 提交内容或触发资源处理 | 否 | 不保证 |
| PUT | 创建或替换目标资源表示 | 否 | 是 |
| PATCH | 对资源进行部分修改 | 否 | 不保证，取决于具体操作 |
| DELETE | 删除目标资源 | 否 | 是 |
| OPTIONS | 查询通信选项或支持的功能 | 是 | 是 |
| CONNECT | 建立隧道，常用于代理场景 | 否 | 否 |
| TRACE | 回显请求，用于诊断 | 是 | 是 |

表格中的安全与幂等指 HTTP 方法的规范语义，而不是说所有服务器实现都一定正确遵守这些语义。TRACE 等方法在生产环境中也可能出于安全考虑被禁用。

### 11. OPTIONS 请求及其应用场景

OPTIONS 用于查询目标资源支持的通信选项，也可以用于检查服务器支持的请求能力。

常见应用场景有两个。

**场景一：查询服务器支持的方法**

客户端可以向资源发送 OPTIONS 请求，服务器可能通过 `Allow` 响应头返回支持的方法。

**场景二：CORS 预检请求**

当浏览器发起某些跨域请求时，可能先发送 OPTIONS 预检请求，询问服务器是否允许指定来源、方法和请求头。

例如：

```http
OPTIONS /api/users HTTP/1.1
Origin: https://frontend.example
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type, authorization
```

服务器可能返回：

```http
Access-Control-Allow-Origin: https://frontend.example
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, Authorization
```

如果预检检查通过，浏览器才会继续发送对应的实际请求。

需要注意：并非所有跨域请求都会触发预检。CORS 也是浏览器的跨域访问控制机制，不等同于用户身份认证或服务器授权。

## 四、HTTP 状态码

### 12. 常见 HTTP 状态码

HTTP 状态码分为五大类：

| 类别 | 含义 | 常见状态码 |
|---|---|---|
| 1xx | 信息性响应 | 100、101 |
| 2xx | 请求成功处理 | 200、201、204 |
| 3xx | 重定向或缓存相关 | 301、302、304 |
| 4xx | 客户端请求相关问题 | 400、401、403、404、405、429 |
| 5xx | 服务器处理失败 | 500、502、503、504 |

常见状态码说明：

- `200 OK`：请求成功。
- `201 Created`：请求成功并创建了资源。
- `204 No Content`：请求成功，但响应没有内容。
- `301 Moved Permanently`：资源已永久移动。
- `302 Found`：资源临时重定向。
- `304 Not Modified`：条件请求验证后，资源未发生需要重新传输的变化。
- `400 Bad Request`：请求格式或内容存在问题。
- `401 Unauthorized`：缺少有效的身份认证凭据，或凭据无效。
- `403 Forbidden`：服务器拒绝执行请求。
- `404 Not Found`：未找到目标资源。
- `405 Method Not Allowed`：目标资源不支持当前请求方法。
- `429 Too Many Requests`：请求过于频繁。
- `500 Internal Server Error`：服务器内部错误。
- `502 Bad Gateway`：网关从上游服务器获得了无效响应。
- `503 Service Unavailable`：服务器暂时无法处理请求。
- `504 Gateway Timeout`：网关等待上游响应超时。

### 13. HTTP 304 状态码越多越好吗？

304 Not Modified 通常出现在协商缓存场景中，表示服务器确认客户端缓存的资源仍然可用，客户端可以继续使用已有缓存，不必重新传输完整的资源内容。

典型过程如下：

```http
GET /app.js HTTP/1.1
If-None-Match: "abc123"
```

如果服务器确认资源的实体标签没有变化，可能返回：

```http
HTTP/1.1 304 Not Modified
ETag: "abc123"
```

此时通常不需要再次传输完整的响应体。

**304 并不是错误，也不存在越多越好或越少越好的绝对结论。**

- 如果静态资源较大、缓存验证频繁，合理的 304 可以减少重复传输。
- 如果资源本来就很小，验证请求本身也会产生网络开销。
- 如果资源经常变化，返回新的 200 响应可能完全正常。
- 如果资源不应频繁变化，可以考虑通过合理的强缓存策略减少验证请求。

不能仅根据 304 的数量判断网站质量、搜索引擎权重或收录情况。更应该结合缓存命中率、资源大小、更新频率、响应耗时和实际业务需求分析。

## 五、HTTP 缓存机制

### 14. 强缓存与协商缓存

浏览器缓存可以减少网络请求、降低服务器压力并加快页面加载。常见策略分为强缓存和协商缓存。

#### 强缓存

强缓存有效时，浏览器可以直接使用缓存资源，不必向服务器验证该资源是否更新。

常见响应头：

- `Cache-Control`
- `Expires`

例如：

```http
Cache-Control: max-age=3600
```

表示响应在规定的新鲜度时间内可以被缓存直接复用，实际行为还会受到其他缓存指令和缓存上下文影响。

`Expires` 使用绝对时间指定过期时刻；`Cache-Control: max-age` 使用相对时长。通常现代 Web 开发更优先使用 Cache-Control。

常见指令：

- `max-age=3600`：指定新鲜度时长。
- `no-cache`：使用缓存前需要验证，不等于禁止存储。
- `no-store`：要求缓存不要存储该响应。
- `private`：响应只能由私有缓存存储，不应被共享缓存存储。
- `public`：允许共享缓存存储，具体仍受其他规则约束。

#### 协商缓存

当缓存需要验证资源是否更新时，浏览器向服务器发送条件请求。

常见的两组请求头和响应头如下：

| 响应头 | 对应请求头 | 作用 |
|---|---|---|
| `ETag` | `If-None-Match` | 通过实体标签验证资源版本 |
| `Last-Modified` | `If-Modified-Since` | 通过资源最后修改时间验证 |

例如：

```http
GET /style.css HTTP/1.1
If-Modified-Since: Tue, 20 Oct 2026 08:00:00 GMT
```

如果资源没有发生需要重新传输的变化，服务器可能返回 304；如果资源发生变化，则返回新的资源表示，通常是 200。

`ETag` 一般比单纯的修改时间更适合表达资源版本差异，但最终采用哪种验证器取决于服务器实现和缓存策略。

#### 前端开发中的缓存实践

- 带内容哈希的 JS、CSS 等构建产物，可以配置较长的缓存时间。
- HTML 入口文件通常需要更谨慎的缓存策略，避免用户长期使用旧版本资源引用。
- 需要及时变化的数据接口，不应盲目配置长时间强缓存。
- 用户隐私数据应根据业务场景设置适当的缓存策略。

## 六、HTTP 版本演进

### 15. HTTP/1.0 和 HTTP/1.1 的区别

| 对比维度 | HTTP/1.0 | HTTP/1.1 |
|---|---|---|
| 连接管理 | 通常使用短连接 | 默认使用持久连接 |
| Host 请求头 | 没有普遍强制要求 | HTTP/1.1 请求通常必须提供 |
| 范围请求 | 支持情况有限，非统一常用能力 | 支持标准化的 Range 范围请求 |
| 缓存 | 有基本缓存机制 | 缓存控制能力进一步完善 |
| 请求方法 | 基本方法 | 增加和完善了 PUT、OPTIONS 等方法及相关语义 |
| 管道化 | 不支持标准化 HTTP/1.1 管道化 | 支持管道化，但实际应用较少 |

#### 持久连接

HTTP/1.1 默认使用持久连接，可以通过一个 TCP 连接传输多个 HTTP 请求和响应，减少反复建立 TCP 连接带来的开销。

如果希望关闭连接，可以使用：

```http
Connection: close
```

需要注意，HTTP/1.0 并不是绝对不能使用持久连接，只是其默认行为与 HTTP/1.1 不同。

#### Range 范围请求

客户端可以通过 `Range` 请求资源的一部分，例如下载文件的指定区间。

```http
GET /video.mp4 HTTP/1.1
Range: bytes=0-1023
```

服务器支持范围请求时，可以返回 `206 Partial Content`，并在适当情况下通过 `Content-Range` 描述返回区间。

### 16. HTTP/1.1 和 HTTP/2 的区别

HTTP/2 在保留 HTTP 请求与响应语义的基础上，优化了连接内的数据传输方式。

#### 二进制分帧

HTTP/1.1 的报文头部主要采用文本格式；HTTP/2 使用二进制帧传输协议数据。

HTTP/2 将头部、数据等信息拆分为帧，并通过流 ID 标识它们所属的逻辑流，为多路复用提供了基础。

#### 多路复用

HTTP/1.1 的普通请求响应模式可能受到串行等待的影响，管道化虽然允许连续发送请求，但响应仍需按照请求顺序返回。

HTTP/2 可以在一个 TCP 连接上交错传输多个流的帧，不要求不同请求的完整响应依次传输。

这样可以减少 HTTP/1.1 层面的队头阻塞。

但是，HTTP/2 仍然基于 TCP。如果 TCP 连接中的某个数据包丢失，TCP 层的有序交付机制可能让多个 HTTP/2 流一起等待，因此 HTTP/2 并没有彻底解决传输层队头阻塞。

#### 头部压缩：HPACK

HTTP/2 使用 HPACK 压缩头部信息，主要通过以下机制减少重复数据：

- 静态表：提供预定义的常见头部字段及值。
- 动态表：存储通信过程中可以复用的头部字段。
- 索引表示：通过索引引用已有条目。
- Huffman 编码：用于压缩部分字符串表示。

需要纠正一个常见误区：**HTTP/2 的头部压缩并不是简单地先使用 gzip 压缩整个头部**。它使用专门设计的 HPACK 机制。

#### 服务器推送

HTTP/2 曾定义服务器推送能力，允许服务器在特定条件下主动推送客户端可能需要的资源。

但它在现代浏览器和实际 Web 开发中的支持与使用受到限制，不应将它当作 HTTP/2 的必然性能优势。实际优化应以测量结果为依据。

### 17. HTTP/2 的头部压缩算法 HPACK 是怎样的？

HPACK 是 HTTP/2 的头部压缩机制，目标是减少重复传输头部字段带来的开销。

假设多个请求都包含相同的头部：

```http
Accept: application/json
User-Agent: ExampleBrowser
```

如果每次都完整传输相同字符串，会产生重复开销。HPACK 可以通过索引或表中的条目引用已有信息，而不必反复传输完整内容。

HPACK 的主要组成部分：

1. **静态表**：保存协议预定义的常见头部条目。
2. **动态表**：维护通信过程中可复用的头部条目。
3. **索引编码**：使用索引表示已知条目。
4. **Huffman 编码**：压缩字符串表示。

动态表会随着编码过程变化，因此编码端和解码端必须按照协议同步维护相应状态。

HTTP/3 不使用 HPACK，而使用 QPACK。QPACK 针对 QUIC 多路复用的特点调整了头部压缩设计，以避免头部压缩依赖导致不必要的跨流阻塞。

### 18. HTTP/2 和 HTTP/3 的区别

HTTP/3 运行在 QUIC 之上，而 QUIC 使用 UDP 作为底层数据报传输协议，并在其上实现可靠传输、拥塞控制、加密和多路复用等能力。

| 对比维度 | HTTP/2 | HTTP/3 |
|---|---|---|
| 底层传输 | TCP | QUIC，基于 UDP |
| 多路复用 | 支持 | 支持 |
| 丢包影响 | TCP 丢包可能阻塞同一连接上的多个流 | 通常只阻塞需要丢失数据的流，不会因单个流的数据丢失而必然阻塞其他流 |
| 头部压缩 | HPACK | QPACK |
| 加密 | 可通过 TLS 使用，HTTPS 场景中通常使用 TLS | QUIC 集成 TLS 1.3 加密机制 |
| 连接建立 | TCP 建连，HTTPS 还需要 TLS 握手 | QUIC 集成传输与加密握手，通常可以减少建连往返时延 |

#### HTTP/3 为什么使用 QUIC？

TCP 在一个连接中提供有序字节流。如果一个 TCP 数据段丢失，即使其他 HTTP/2 流的数据已经到达，也可能因为 TCP 必须按序交付而等待重传。

QUIC 为不同的流维护相互独立的可靠传输状态。因此，一个流的数据丢失通常不会要求其他流也等待该数据的重传。

这解决的是 TCP 层面的跨流队头阻塞问题，但并不意味着 HTTP/3 不存在任何阻塞或网络延迟。

#### HTTP/3 一定比 HTTP/2 快吗？

不一定。HTTP/3 在网络变化、丢包、连接迁移等场景中可能有优势，但实际性能仍取决于网络环境、服务器部署、连接复用情况、资源大小和浏览器实现。

此外，QUIC 支持在满足条件时进行 0-RTT 数据发送，但 0-RTT 存在重放风险，并非所有请求都适合使用。不能简单地认为每次 HTTP/3 连接都只需要 0～1 个 RTT。

## 七、HTTPS 与连接管理

### 19. HTTP 和 HTTPS 的区别

HTTPS 可以理解为在 HTTP 通信上使用 TLS 提供安全保护。

| 对比维度 | HTTP | HTTPS |
|---|---|---|
| 数据加密 | 协议本身不提供传输加密 | 使用 TLS 保护通信内容 |
| 身份验证 | 本身不验证服务端证书 | 通常通过证书验证服务端身份 |
| 完整性保护 | 本身不提供密码学完整性保护 | TLS 可提供传输数据的完整性保护 |
| 默认端口 | 80 | 443 |
| 连接开销 | 取决于底层连接 | 还涉及 TLS 的建连与加密处理 |

HTTPS 的主要作用是降低通信内容被窃听、篡改以及服务端身份被冒充的风险。

不过，HTTPS 并不能自动防止所有安全问题。例如，服务器漏洞、XSS、业务权限校验错误和敏感信息泄露仍需要应用层处理。

### 20. HTTPS 的 TLS 握手过程

在典型的 TLS 1.3 完整握手中，可以概括为以下过程：

1. **客户端发起协商**：发送支持的 TLS 版本、密码套件、密钥交换参数等信息。
2. **服务端返回协商结果**：选择参数并发送密钥交换相关信息、证书及相关证明。
3. **客户端验证服务端身份**：检查证书链、域名、有效期及其他验证条件。
4. **双方建立会话密钥**：通过密钥交换过程协商共享密钥材料，派生后续通信所使用的密钥。
5. **验证握手并开始加密通信**：双方验证握手信息后，使用协商出的密钥保护后续数据。

这里有两个常见误区：

- 现代 TLS 不应被简单描述为“服务器用公钥加密随机数，客户端用私钥解密”。现代握手通常采用临时密钥交换机制，例如基于 ECDHE 的密钥协商。
- TLS 1.3 的典型完整握手通常需要约 1 个 RTT，而 TLS 1.2 的常见完整握手通常需要更多往返。具体过程会受到协议版本、恢复会话、网络环境等因素影响。

HTTPS 的安全性来自加密、完整性保护和身份验证等机制的组合，而不是仅仅因为“有一张证书”。

### 21. 什么是 Keep-Alive？

Keep-Alive 通常指 HTTP 持久连接：在一次请求响应完成后，底层连接仍然保持可用，以便继续传输后续请求。

HTTP/1.0 通常默认使用非持久连接；HTTP/1.1 默认使用持久连接。

HTTP/1.1 中可以通过：

```http
Connection: close
```

要求在完成当前响应后关闭连接。

持久连接的优点：

- 减少反复建立 TCP 连接的开销。
- 降低后续请求的连接建立时延。
- 减少频繁创建和释放连接造成的系统开销。

潜在问题：

- 长时间空闲的连接会占用一定资源。
- 服务器需要配置空闲超时、最大连接数等策略。
- 连接复用仍需要考虑网络故障、连接关闭和请求失败等情况。

另外，HTTP/2 和 HTTP/3 的连接复用机制与 HTTP/1.1 不完全相同，不应将 HTTP/1.1 的 `Connection: keep-alive` 用法直接套用到 HTTP/2 或 HTTP/3。

## 八、HTTP 性能与队头阻塞

### 22. HTTP 的性能主要受什么影响？

HTTP 的性能受到多个因素影响，包括连接建立、请求响应时延、网络带宽、丢包、数据压缩、缓存命中率、服务端处理耗时以及资源数量等。

#### 持久连接

复用已有连接可以减少重复建连的成本。对于 HTTP/1.1，这通常意味着使用持久 TCP 连接；对于 HTTP/2，则可以在同一个 TCP 连接上复用多个 HTTP 流。

#### HTTP/1.1 管道化

管道化允许客户端在等待前一个响应时继续发送后续请求，但服务器需要按照请求顺序返回响应。

如果第一个响应很慢，后面的响应也可能受到阻塞，因此管道化在实际浏览器中使用有限。

#### 队头阻塞

队头阻塞指队列前面的任务阻碍后续任务继续完成。

不同协议中的队头阻塞需要区分：

- **HTTP/1.1**：在同一连接中，请求响应顺序和管道化可能导致应用层队头阻塞。
- **HTTP/2**：多路复用减少了 HTTP 层的串行等待，但底层 TCP 丢包仍可能阻塞多个流的数据交付。
- **HTTP/3**：QUIC 的独立流传输减少了单个流丢包对其他流的影响。

#### 域名分片

域名分片是早期 HTTP/1.x 场景中曾采用的一种优化方式：将资源分布在多个域名下，以增加可并行建立的连接数。

但它会增加 DNS 查询、连接建立和管理开销。对于 HTTP/2 和 HTTP/3，通常应优先考虑连接复用，不宜盲目进行域名分片。

## 九、浏览器输入 URL 后发生了什么？

这是前端面试中的经典综合题，可以按照“解析地址 → 缓存检查 → 网络寻址 → 建立连接 → 发送请求 → 服务端响应 → 页面渲染”进行回答。

### 23. 完整访问流程

#### 第一步：解析 URL

浏览器解析输入的地址，识别协议、主机名、端口、路径和查询参数等信息。

如果输入内容不像完整 URL，浏览器可能将其作为搜索词交给默认搜索引擎处理。

#### 第二步：检查缓存

浏览器可能根据缓存策略直接使用有效缓存。

如果缓存需要验证，浏览器可能发起条件请求；如果缓存失效或不存在，则需要访问网络获取资源。

#### 第三步：DNS 解析

浏览器需要获得目标域名对应的 IP 地址。

DNS 查询可能涉及浏览器缓存、操作系统缓存、递归 DNS 解析器缓存，以及根域名、顶级域名和权威域名服务器等环节。

实际查询链路会受到缓存、DNS over HTTPS、DNS over TLS 和网络配置等因素影响，并不保证每次访问都会从根域名服务器开始查询。

#### 第四步：确定链路层目标地址

当数据需要通过以太网等链路发送时，设备需要获得下一跳的链路层地址。

- 如果目标 IP 位于本地子网，通常需要解析目标主机的链路层地址。
- 如果目标 IP 不在本地子网，则通常解析默认网关的链路层地址，再由网关进行转发。

IPv4 网络中常见的是 ARP，IPv6 网络中使用邻居发现机制。浏览器本身通常不直接执行这些操作，而是由操作系统网络栈处理。

#### 第五步：建立传输连接

如果访问 HTTP/1.1 或 HTTP/2，通常需要建立 TCP 连接；如果访问 HTTPS，还需要完成 TLS 协商，除非复用了已有连接或采用会话恢复等机制。

如果访问 HTTP/3，则使用 QUIC 建立连接，传输和加密握手的流程与 TCP + TLS 不同。

#### 第六步：发送 HTTP 请求

连接建立后，浏览器发送 HTTP 请求，其中包括请求方法、目标资源、请求头以及可能存在的请求体。

例如：

```http
GET /index.html HTTP/1.1
Host: www.example.com
Accept: text/html
```

#### 第七步：服务器处理请求并返回响应

服务器可能经过反向代理、负载均衡、缓存、应用服务和数据库等环节，最终生成 HTTP 响应。

响应中包括状态码、响应头，以及适用情况下的响应体。

#### 第八步：浏览器解析并渲染页面

对于 HTML 页面，浏览器大致执行以下工作：

1. 解析 HTML，逐步构建 DOM。
2. 解析 CSS，构建 CSSOM。
3. 根据 DOM 和 CSSOM 等信息生成渲染所需的结构。
4. 计算布局，确定元素的位置和尺寸。
5. 绘制页面，并在需要时进行图层合成。
6. 执行 JavaScript，并根据脚本执行结果继续更新 DOM、样式和页面。

脚本加载与执行可能影响 HTML 解析和首次渲染。普通同步脚本、`async` 和 `defer` 的行为有所不同，具体还与脚本类型和执行时机有关。

#### 第九步：后续资源加载与连接复用

浏览器继续请求 CSS、JavaScript、图片、字体等子资源。不同资源的请求可能并行发起，也可能受到依赖关系、缓存策略和浏览器调度的影响。

如果连接可以复用，后续请求通常不必重新完成整套建连过程。

**补充：TCP 四次挥手并不是每次页面访问结束时必然发生。** 连接可能继续复用，也可能由浏览器、服务器或中间设备在适当时机关闭。若确实需要关闭 TCP 连接，通常会经历 FIN、ACK 等关闭过程。

## 十、前端开发中的常见问题

### 24. 页面有多张图片时，HTTP 是怎样加载的？

浏览器会根据资源依赖关系、连接协议、缓存状态、网络条件和调度策略，安排图片等资源的请求。

#### HTTP/1.1

浏览器通常会对同一主机名建立一定数量的并发连接，具体数量取决于浏览器和实现。多个连接可以让不同请求并行传输，但也会增加连接管理开销。

#### HTTP/2

HTTP/2 支持在同一个 TCP 连接上多路复用多个请求的帧，因此多个图片资源可以共享连接，不必为每张图片单独建立 TCP 连接。

但图片仍需要下载、解码、布局和绘制，并不是使用 HTTP/2 就一定能瞬间显示全部图片。

#### 实际优化方式

- 使用合适尺寸的图片，避免传输远大于展示尺寸的资源。
- 使用 WebP、AVIF 等合适的图片格式。
- 对非首屏图片使用懒加载。
- 设置图片的宽高，减少布局偏移。
- 合理配置缓存策略。
- 根据业务需要使用 CDN。
- 通过性能工具识别真正的瓶颈，而不是只关注 HTTP 版本。

### 25. HTTP 有什么优点和缺点？

#### 优点

- 采用清晰的请求响应模型，容易理解和实现。
- 支持多种方法、状态码、请求头和响应头。
- 能够传输多种类型的资源。
- 具有缓存、认证、内容协商和重定向等丰富机制。
- 具有良好的扩展性，适用于网页、接口和多种网络服务。

#### 局限与风险

- HTTP 本身的无状态特征意味着应用需要自行管理用户会话和业务状态。
- 未使用 TLS 的 HTTP 不提供传输层加密，通信内容可能被窃听或篡改。
- 建连、请求响应、网络丢包和大量资源传输可能带来时延。
- 缓存、跨域、安全和连接管理需要正确配置，否则可能产生性能或安全问题。

需要注意，无状态是 HTTP 的设计特点，并非一定的缺陷；使用 HTTPS 也不能替代应用层的身份认证、权限控制和安全编码。

## 总结

HTTP 是前端开发中最重要的基础协议之一。学习时不要只背请求头、状态码和版本区别，更要理解这些机制解决了什么问题。

建议重点掌握以下知识链路：

1. **请求与响应**：请求方法、报文结构、状态码和 Content-Type。
2. **缓存机制**：强缓存、协商缓存、ETag、Last-Modified 和 304。
3. **版本演进**：HTTP/1.1 持久连接、HTTP/2 多路复用、HTTP/3 的 QUIC。
4. **安全机制**：HTTPS、TLS、Cookie、认证与 CORS。
5. **浏览器访问流程**：URL 解析、DNS、连接建立、服务器响应和页面渲染。
6. **性能优化**：资源缓存、连接复用、图片优化、懒加载和网络诊断。

理解每个机制背后的问题与解决方案，才能在面试追问和实际开发中灵活运用。
