# 浏览器安全：XSS、CSRF、中间人攻击与网络劫持

## 一、前言

浏览器安全是前端面试中的高频考点，也是 Web 应用开发中必须关注的问题。

前端应用不仅需要正确地渲染页面，还需要处理用户输入、Cookie、跨域请求、第三方资源以及网络通信等安全问题。如果缺乏有效的安全措施，攻击者可能利用浏览器的执行机制或身份认证机制，窃取用户信息、伪造用户操作，甚至篡改页面内容。

本文主要介绍以下知识点：

- XSS：跨站脚本攻击
- CSRF：跨站请求伪造
- CSP：内容安全策略
- Cookie 安全属性与 SameSite
- 中间人攻击与 HTTPS
- iframe 和第三方依赖的安全风险
- DNS 劫持与 HTTP 劫持

## 二、XSS：跨站脚本攻击

### 2.1 什么是 XSS？

XSS（Cross-Site Scripting，跨站脚本攻击）是一种代码注入攻击。攻击者将恶意脚本注入网页，当其他用户访问相关页面时，恶意脚本可能在用户的浏览器中执行。

XSS 的核心问题是：**应用没有正确处理不可信数据，导致数据被浏览器当作可执行代码解析。**

例如，某个评论功能允许用户提交内容，服务端又将评论内容直接拼接到 HTML 中。如果攻击者提交的内容包含恶意脚本，其他用户查看评论时就可能触发攻击。

XSS 可能造成以下危害：

1. 读取页面中的敏感信息。
2. 在用户身份下发起请求，执行未经用户预期的操作。
3. 篡改页面内容，伪造登录框或诱导用户输入密码。
4. 读取可被 JavaScript 访问的 Cookie、LocalStorage 等数据。
5. 利用用户浏览器发送大量请求，消耗服务端资源。

需要注意：设置了 `HttpOnly` 的 Cookie 不能被普通页面 JavaScript 直接读取，但 XSS 仍可能利用当前用户的登录状态执行操作。

### 2.2 XSS 的三种类型

#### 1. 存储型 XSS

存储型 XSS（Stored XSS）是指恶意内容被保存到数据库或其他持久化存储中，并在后续页面渲染时触发。

攻击过程：

1. 攻击者向论坛、评论区或私信系统提交恶意内容。
2. 应用将内容保存到数据库。
3. 其他用户访问相关页面。
4. 服务端或前端将恶意内容插入页面，浏览器执行其中的恶意代码。

常见场景包括论坛发帖、商品评论、用户昵称、站内信等。

**核心特征：恶意内容被持久化保存，后续访问者可能受到影响。**

#### 2. 反射型 XSS

反射型 XSS（Reflected XSS）是指应用将请求中的不可信数据直接反射到响应内容中，导致浏览器执行恶意代码。

攻击过程：

1. 攻击者构造包含恶意参数的 URL。
2. 用户被诱导访问该 URL。
3. 服务端读取参数，并将其不安全地拼接到 HTML 响应中。
4. 浏览器解析响应时执行恶意代码。

常见场景包括搜索结果页、错误提示页和根据 URL 参数动态生成内容的页面。

**核心特征：恶意数据通常来自当前请求，并被服务端不安全地反射到响应中。**

#### 3. DOM 型 XSS

DOM 型 XSS（DOM-based XSS）是指前端 JavaScript 将不可信数据传入不安全的 DOM 操作接口，导致浏览器将数据当作 HTML 或脚本内容解析执行。

例如：

```javascript
const params = new URLSearchParams(location.search);
const keyword = params.get('keyword');

// 不安全：将不可信数据作为 HTML 解析
document.querySelector('#result').innerHTML = keyword;
```

如果 `keyword` 中包含恶意 HTML，浏览器可能创建不应该存在的元素，甚至执行其中的事件处理代码。

更安全的写法是：

```javascript
const params = new URLSearchParams(location.search);
const keyword = params.get('keyword');

document.querySelector('#result').textContent = keyword;
```

`textContent` 会将内容作为文本插入，而不是将其解析为 HTML。

需要注意，DOM 型 XSS 经常由前端代码中的不安全数据流引起，但不能简单地认为 XSS 一定是服务端漏洞，或者 DOM 型 XSS 一定与服务端无关。判断重点是恶意数据如何进入页面，以及最终如何被浏览器处理。

### 2.3 三种 XSS 的区别

| 类型 | 恶意数据来源 | 典型特点 |
| --- | --- | --- |
| 存储型 | 数据库或持久化存储 | 一次注入，可能影响多个访问者 |
| 反射型 | 当前请求参数 | 恶意数据被服务端反射到响应 |
| DOM 型 | URL、用户输入或其他客户端数据 | 前端 JavaScript 将不可信数据传入危险 DOM 接口 |

三者并非完全互斥。例如，一个恶意数据也可能同时涉及服务端反射和前端 DOM 操作。

### 2.4 如何防御 XSS？

#### 1. 根据输出上下文进行编码

这是防御 XSS 的核心措施之一。

不同位置需要不同的处理方式，例如 HTML 文本、HTML 属性、URL 和 JavaScript 字符串所需的安全处理并不相同。

- 普通文本优先使用 `textContent`。
- 使用框架的默认文本插值功能，不要随意绕过转义机制。
- 避免将不可信数据拼接进 `innerHTML`、`outerHTML` 或 `document.write()`。
- 如果业务必须渲染富文本，应使用经过维护和安全审查的 HTML 清理库。
- 对 URL 协议和目标地址进行校验，避免不可信链接带来的风险。

注意：单纯过滤几个特殊字符通常不够，因为不同上下文的解析规则不同。

#### 2. 使用 CSP

CSP（Content Security Policy，内容安全策略）是一种浏览器安全机制，用于限制页面可以加载和执行哪些资源。

例如：

```http
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'
```

这条策略的含义包括：

- 默认情况下，资源只能从当前源加载。
- 脚本只允许从当前源加载。
- 禁止加载插件对象。
- 限制文档基础 URL 的设置。

实际项目需要结合 CDN、脚本加载方式等调整策略。严格的 CSP 通常应优先考虑 nonce 或 hash 等机制，避免依赖宽松的脚本白名单。

CSP 可以降低部分 XSS 攻击的影响，但不能代替输出编码和不可信数据处理。

CSP 通常通过 HTTP 响应头配置，也可以通过 HTML 的 `meta` 标签配置，但 `meta` 方式存在部分指令不受支持的限制。

#### 3. 使用 HttpOnly 保护 Cookie

服务端可以设置：

```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax
```

其中：

- `HttpOnly`：阻止普通 JavaScript 通过 `document.cookie` 读取该 Cookie。
- `Secure`：只通过 HTTPS 发送 Cookie。
- `SameSite=Lax`：限制 Cookie 在部分跨站请求中的发送。

这些属性保护的是 Cookie 的访问和发送行为，并不意味着 XSS 漏洞已经被修复。

即使攻击者无法读取 Cookie，也可能借助用户当前的登录状态执行请求。

#### 4. 谨慎使用危险 DOM API

前端开发时，应尽量避免直接拼接 HTML 字符串。

React、Vue 等框架的默认文本渲染机制通常会对文本进行转义，但以下情况仍需要格外小心：

- React 的 `dangerouslySetInnerHTML`
- Vue 的 `v-html`
- 手动操作 `innerHTML`
- 不安全的第三方富文本渲染组件

框架并不能自动保护所有手动 DOM 操作和第三方库。

## 三、CSRF：跨站请求伪造

### 3.1 什么是 CSRF？

CSRF（Cross-Site Request Forgery，跨站请求伪造）是指攻击者诱导已登录用户访问恶意页面，借助浏览器自动携带的身份凭证，向目标网站发起用户并不知情或不希望执行的请求。

例如，用户已经登录某个银行网站，浏览器保存了登录 Cookie。此时，用户访问恶意网站，恶意网站可能尝试诱导浏览器向银行网站发送转账请求。

如果目标网站只依赖自动携带的 Cookie 判断身份，又没有进行有效的请求来源或防伪验证，就可能受到攻击。

**CSRF 的核心是利用浏览器自动携带身份凭证的机制，伪造用户发起的请求。**

### 3.2 CSRF 的常见形式

#### 1. GET 请求

如果网站错误地使用 GET 请求执行转账、删除等状态修改操作，攻击者可能利用图片、链接等元素诱导浏览器发起请求。

```html
<img src="https://example.com/transfer?to=attacker&amount=100">
```

这只是示意性的攻击场景。它能否成功取决于目标网站的接口设计、Cookie 策略和防护机制。

正确做法是：GET 请求应当用于获取资源，而不是执行重要的状态修改操作。

#### 2. POST 请求

攻击者可能构造一个隐藏表单，并诱导浏览器自动提交：

```html
<form action="https://example.com/change-email" method="POST">
  <input name="email" value="attacker@example.com">
</form>
```

如果目标站点接受该请求，并且身份验证只依赖浏览器自动携带的凭证，就可能存在 CSRF 风险。

#### 3. 链接诱导

攻击者可能诱导用户点击一个看似正常的链接。如果链接触发了不安全的状态修改接口，也可能产生安全问题。

因此，不能依赖“用户需要点击”来保证请求安全。

### 3.3 如何防御 CSRF？

#### 1. 使用 CSRF Token

服务端为用户会话生成不可预测的 Token，并要求客户端在提交状态修改请求时提供该 Token。

例如：

```http
POST /api/profile
Content-Type: application/json
X-CSRF-Token: random-token
```

服务端验证 Token 是否有效后，再决定是否处理请求。

攻击者通常无法从另一个源读取目标站点返回的 Token，因此很难构造合法请求。

对于分布式部署，可以采用共享会话存储，或者使用经过正确设计的无状态 Token 验证机制。并不是每台服务器都必须独立保存一份 Token。

#### 2. 使用 SameSite Cookie

`SameSite` 用于控制 Cookie 在跨站请求中的发送行为。

| 属性 | 含义 |
| --- | --- |
| `Strict` | 通常仅在同站请求中发送 Cookie |
| `Lax` | 允许部分顶层跨站导航携带 Cookie，常见 GET 导航属于此类 |
| `None` | 允许跨站发送 Cookie，但通常要求同时设置 `Secure` |

例如：

```http
Set-Cookie: sessionId=abc123; Secure; HttpOnly; SameSite=Lax
```

需要注意：

- SameSite 限制的是 Cookie 的发送，不是所有跨站请求。
- `Lax` 并不意味着所有跨站请求都无法携带 Cookie。
- 同站（site）和同源（origin）不是同一个概念。
- 如果站点存在不可信子域或其他漏洞，仍需结合其他防护措施。

#### 3. 校验 Origin 和 Referer

服务端可以检查请求的 `Origin`，必要时结合 `Referer`，判断请求是否来自可信站点。

对于敏感的状态修改操作，如果来源不符合预期，应拒绝处理。

不过，`Origin` 和 `Referer` 可能因浏览器策略、隐私设置或请求类型而缺失，因此服务端应制定明确的校验策略，不能简单地认为所有缺失字段都能安全放行。

此外，普通网页 JavaScript 不能随意伪造浏览器控制的 `Origin` 请求头，但非浏览器客户端可以自行构造请求头，因此来源校验仍需与身份认证等机制配合。

#### 4. 使用双重提交 Cookie

双重提交 Cookie（Double Submit Cookie）要求客户端同时提交 Cookie 中的随机值和请求参数或请求头中的对应值，服务端验证二者是否一致。

需要注意，这种方案不能简单地认为“两个值相等就安全”。Token 的生成、Cookie 域和路径、签名校验以及子域安全都需要正确设计。对于高安全要求的场景，应优先选择经过充分验证的实现方案。

#### 5. 重要操作增加二次确认

对于转账、修改密码、修改绑定手机号等高风险操作，可以增加重新认证、验证码或二次确认等措施。

验证码并不是通用的 CSRF 防护方案，而是用于提高某些操作被自动化滥用的难度。

### 3.4 XSS 和 CSRF 的区别

| 对比项 | XSS | CSRF |
| --- | --- | --- |
| 攻击目标 | 在受信任页面执行恶意脚本 | 伪造用户向目标站点发送请求 |
| 核心问题 | 不可信数据被当作代码执行 | 请求缺乏有效的防伪验证 |
| 常见影响 | 窃取页面数据、执行用户操作 | 冒充用户修改数据或执行操作 |
| 主要防护 | 输出编码、HTML 清理、CSP | CSRF Token、SameSite、来源校验 |

二者可能相互影响。特别是，如果网站存在能够执行任意同源脚本的 XSS 漏洞，攻击者可能读取页面中的 CSRF Token，或者直接在用户登录状态下发起请求。

因此，不能仅仅依赖 CSRF 防护来弥补 XSS 漏洞。

## 四、Cookie 与浏览器安全

Cookie 经常用于保存会话标识，是 Web 身份认证中需要重点保护的内容。

### 4.1 Cookie 的重要属性

| 属性 | 作用 |
| --- | --- |
| `HttpOnly` | 防止普通 JavaScript 直接读取 Cookie |
| `Secure` | 限制 Cookie 通过 HTTPS 发送 |
| `SameSite` | 控制 Cookie 在跨站请求中的发送行为 |
| `Domain` | 控制 Cookie 可以适用的域名范围 |
| `Path` | 控制 Cookie 适用的 URL 路径范围 |
| `Max-Age` / `Expires` | 控制 Cookie 的有效期 |

其中，`Domain` 配置过宽可能让更多子域接触到 Cookie，增加安全风险。对敏感会话 Cookie，应尽量缩小适用范围。

如果架构允许，还可以使用带有 `__Host-` 前缀的 Cookie，并遵循其 Secure、Path 和 Domain 限制，以降低部分 Cookie 覆盖和子域相关风险。

### 4.2 LocalStorage 与 Cookie 的区别

| 对比项 | Cookie | LocalStorage |
| --- | --- | --- |
| 默认是否随 HTTP 请求发送 | 满足匹配规则时会 | 不会 |
| JavaScript 是否可读取 | 除非设置 HttpOnly 等限制 | 通常可以 |
| 适用场景 | 会话标识、服务端身份认证 | 客户端非敏感持久化数据 |
| XSS 风险 | HttpOnly 可降低直接读取风险 | 同源恶意脚本通常可以读取 |

不建议将高敏感凭证随意保存在 LocalStorage 中，因为一旦发生 XSS，攻击者可能直接读取其中的数据。

但也不能简单地认为 Cookie 一定比 LocalStorage 安全。具体风险取决于凭证设计、存储方式、脚本执行权限和请求验证机制。

## 五、中间人攻击与 HTTPS

### 5.1 什么是中间人攻击？

中间人攻击（Man-in-the-Middle，MITM）是指攻击者介入通信双方之间，拦截、转发甚至篡改通信内容，使双方误以为自己正在与真正的对端直接通信。

在缺乏有效身份验证的通信场景中，攻击者可能尝试：

1. 拦截客户端与服务端之间的通信。
2. 向客户端提供伪造的服务端身份信息。
3. 尝试获取或替换通信密钥。
4. 解密、篡改或转发通信数据。

原始的中间人攻击示意图如下：

```text
客户端  ←→  攻击者  ←→  服务端
          拦截、转发、
          伪造或篡改
```

需要注意：在正确验证证书的现代 HTTPS/TLS 通信中，攻击者不能仅凭截获服务器公钥，就直接解密会话数据。TLS 会通过证书验证、密钥协商和完整性保护等机制防御常见的中间人攻击。

### 5.2 HTTPS 如何防范中间人攻击？

HTTPS = HTTP + TLS。

TLS 提供的主要安全能力包括：

- **机密性**：防止通信内容被未经授权地读取。
- **完整性**：检测通信内容是否被篡改。
- **身份认证**：通过证书验证服务端身份，降低连接到假冒服务器的风险。

开发和部署时还应注意：

1. 全站使用 HTTPS。
2. 不忽略浏览器的证书错误。
3. 正确配置证书链和域名。
4. 使用 HSTS，降低用户被降级到 HTTP 的风险。
5. 避免页面混合加载不安全的 HTTP 资源。

HTTPS 并不能解决所有安全问题。例如，服务器自身被入侵、用户设备感染恶意软件、网站存在 XSS 漏洞，仍然可能造成数据泄露。

## 六、iframe 与第三方依赖安全

### 6.1 iframe 的安全风险

`iframe` 可以嵌入其他网页，但被嵌入的内容可能来自第三方站点。

如果不加限制，第三方页面可能展示欺骗性内容，或者利用嵌入环境进行不符合预期的交互。

常见防护方式包括：

- 使用 `sandbox` 限制 iframe 的能力。
- 对需要的权限进行最小化授权。
- 使用 CSP 的 `frame-ancestors` 限制哪些站点可以嵌入当前页面。
- 使用 `X-Frame-Options` 作为兼容性较好的旧式嵌入限制手段。
- 对 `postMessage` 进行严格校验。

例如：

```html
<iframe
  src="https://trusted.example.com"
  sandbox="allow-scripts"
  title="嵌入内容">
</iframe>
```

`sandbox` 中允许的能力越多，限制越少，应当根据实际需求谨慎添加。

### 6.2 postMessage 的安全注意事项

当父页面与 iframe 需要跨源通信时，可以使用 `postMessage`。

发送消息时应尽量指定明确的目标源：

```javascript
iframe.contentWindow.postMessage(
  { type: 'INIT' },
  'https://trusted.example.com'
);
```

接收消息时应检查消息来源和数据格式：

```javascript
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://trusted.example.com') {
    return;
  }

  if (!event.data || event.data.type !== 'INIT') {
    return;
  }

  // 处理经过校验的消息
});
```

不能因为消息事件来自 `message` 监听器，就认为其内容可信。还应校验消息结构、字段类型以及具体业务权限。

### 6.3 恶意第三方依赖

前端项目通常会依赖 npm 包、UI 组件库、统计脚本和 CDN 资源。如果第三方依赖被植入恶意代码，可能造成敏感数据泄露或代码执行。

常见措施包括：

- 优先选择维护活跃、来源可信的依赖。
- 定期检查依赖漏洞和版本更新。
- 使用锁文件，控制依赖版本。
- 减少不必要的依赖与第三方脚本。
- 对外部脚本使用 Subresource Integrity（SRI）等完整性校验机制，前提是资源加载方式支持。
- 通过 CSP 限制脚本和其他资源的来源。

## 七、网络劫持：DNS 劫持与 HTTP 劫持

### 7.1 DNS 劫持

DNS 的作用是将域名解析为 IP 地址。

DNS 劫持是指攻击者通过篡改 DNS 解析结果等方式，让用户访问域名时连接到非预期的服务器。

例如，用户输入某个网站的域名，却被引导到攻击者控制的 IP 地址。

需要注意：DNS 解析异常并不一定都是恶意劫持，也可能由缓存错误、配置问题或网络故障导致。

### 7.2 HTTP 劫持

HTTP 劫持通常指攻击者或网络中间设备利用 HTTP 明文传输的特点，拦截或篡改请求、响应内容。

例如，用户访问一个使用 HTTP 的网页时，网络中间设备向响应中插入广告，或者将用户重定向到其他页面。

### 7.3 如何防范网络劫持？

- **全站 HTTPS**：通过 TLS 保护请求与响应的机密性和完整性。
- **启用 HSTS**：让浏览器在后续访问中强制使用 HTTPS。
- **正确验证 TLS 证书**：避免接受无效证书。
- **使用可信 DNS 服务**：降低部分 DNS 篡改风险，但不能代替 HTTPS。
- **避免混合内容**：不要在 HTTPS 页面中加载不安全的 HTTP 脚本或其他敏感资源。

HTTPS 能够有效防止常见的传输过程篡改，但无法阻止所有 DNS 欺骗、终端入侵、恶意扩展或服务器端攻击。

## 八、前端安全开发清单

实际开发时，可以从以下几个方面检查安全问题。

### 输入与渲染

- [ ] 对不可信输入进行合理校验。
- [ ] 根据输出上下文进行编码。
- [ ] 普通文本优先使用 `textContent` 或框架的安全文本插值。
- [ ] 避免直接拼接不可信 HTML。
- [ ] 富文本经过可信的 HTML 清理流程。

### 身份认证与请求

- [ ] 会话 Cookie 根据场景配置 `HttpOnly`、`Secure` 和 `SameSite`。
- [ ] 重要状态修改接口使用适当的 CSRF 防护。
- [ ] 服务端对权限和业务参数进行验证。
- [ ] 不将前端校验作为唯一的安全边界。
- [ ] 敏感操作增加必要的重新认证或二次确认。

### 资源与通信

- [ ] 全站使用 HTTPS。
- [ ] 配置合理的 CSP。
- [ ] 谨慎使用 iframe 和第三方脚本。
- [ ] 对 `postMessage` 校验来源和数据。
- [ ] 定期检查第三方依赖的漏洞。

## 九、面试总结

浏览器安全可以从攻击原理和防御措施两个角度理解。

1. **XSS**：不可信数据被当作代码执行。重点掌握存储型、反射型、DOM 型的区别，以及输出编码、HTML 清理、CSP 和 Cookie 保护。
2. **CSRF**：攻击者利用浏览器自动携带身份凭证的机制伪造请求。重点掌握 CSRF Token、SameSite、Origin/Referer 校验，以及 XSS 与 CSRF 的关系。
3. **Cookie 安全**：理解 `HttpOnly`、`Secure`、`SameSite` 的作用和局限。
4. **中间人攻击**：理解攻击者拦截和篡改通信的原理，以及 TLS 的加密、完整性保护和身份认证机制。
5. **iframe 与第三方依赖**：关注权限隔离、消息来源验证、CSP 和依赖供应链风险。
6. **网络劫持**：理解 DNS 劫持与 HTTP 劫持的区别，并掌握 HTTPS 和 HSTS 的防护作用。

对于前端工程师来说，安全不只是过滤输入或增加一个请求头，而是贯穿数据输入、页面渲染、身份认证、接口调用和资源加载的完整开发流程。
