# HTTP 状态码详解：分类、常见状态码与面试重点

HTTP 状态码（HTTP Status Code）是服务器在 HTTP 响应中返回的三位数字，用于表示服务器对请求的处理结果。

在前端开发中，理解 HTTP 状态码有助于排查接口请求失败、处理登录认证、理解浏览器缓存、实现重定向，以及定位 Nginx 和后端服务的问题。

## 一、HTTP 状态码的分类

HTTP 状态码按照第一位数字分为五类。

| 类别 | 英文名称 | 含义 |
|---|---|---|
| 1xx | Informational | 信息性状态码，请求处理仍在进行中 |
| 2xx | Success | 请求已成功接收、理解或处理 |
| 3xx | Redirection | 需要进一步操作，通常涉及重定向或缓存验证 |
| 4xx | Client Error | 请求存在问题，或客户端无权访问资源 |
| 5xx | Server Error | 服务器处理请求时发生错误 |

需要注意：4xx 不一定意味着错误完全由客户端代码造成，例如权限配置、资源策略也可能导致 403；5xx 则表示服务器在处理请求或履行网关职责时遇到了问题。

日常开发中最常见的是 200、201、204、301、302、304、400、401、403、404、405、429、500、502、503 和 504。

## 二、2xx：成功状态码

2xx 表示请求已成功处理，具体含义取决于状态码。

### 1. 200 OK

表示请求成功。

这是最常见的成功状态码。例如，前端通过 `fetch` 获取用户信息，服务器成功处理后返回用户数据，通常会使用 200。

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"id": 1, "name": "Alice"}
```

注意：HTTP 层面的 200 表示请求成功处理，不代表业务逻辑一定成功。例如，某些接口可能在 HTTP 200 响应体中返回业务错误码。

### 2. 201 Created

表示请求成功，并创建了一个或多个资源，常见于 POST 创建资源的场景。

例如，用户注册成功并创建了新的用户资源。

服务器可以通过 `Location` 响应头指明新创建资源的位置。

### 3. 204 No Content

表示请求成功，但响应中没有消息内容。

例如，前端提交修改操作，服务器已经成功处理，不需要返回数据。

```http
HTTP/1.1 204 No Content
```

204 响应不能包含响应内容。前端处理这类接口时，不应该直接调用 `response.json()` 并假定响应体中存在 JSON 数据。

### 4. 205 Reset Content

表示请求成功，并要求客户端重置当前文档或输入视图的内容。

例如，某些表单提交成功后，希望客户端清空输入内容。

它与 204 的区别是：204 只表示没有响应内容，而 205 还表达了重置客户端视图的语义。

### 5. 206 Partial Content

表示服务器成功返回了资源的一部分，通常用于 HTTP 范围请求。

例如，视频播放器只请求视频文件中的一段数据。

```http
GET /video.mp4 HTTP/1.1
Range: bytes=0-999
```

服务器支持并满足范围请求时，可以返回：

```http
HTTP/1.1 206 Partial Content
Content-Range: bytes 0-999/5000
```

这表示返回的是资源中的部分字节，而不是整个文件。

## 三、3xx：重定向与缓存相关状态码

3xx 表示客户端需要进一步操作才能完成预期处理。不过，**3xx 并不全部代表页面跳转**，304 就是一个典型例外。

### 1. 301 Moved Permanently

表示资源已被永久移动到新的 URI，新的地址通常通过 `Location` 响应头指定。

```http
HTTP/1.1 301 Moved Permanently
Location: https://new.example.com/
```

常见场景：

- 网站更换域名，将旧域名永久重定向到新域名。
- 将 HTTP 地址永久重定向到 HTTPS 地址。
- 将旧的资源路径迁移到新的路径。

301 可能影响搜索引擎对新旧 URL 的处理，但搜索引擎最终如何索引仍由其规则决定。

需要注意，301 在实际客户端中可能导致 POST 请求变为 GET，因此涉及请求方法和请求体时，应谨慎选择重定向状态码。

### 2. 302 Found

表示资源目前位于另一个 URI，客户端应临时使用新地址。

常见场景：

- 用户尚未登录，访问需要认证的页面时，被重定向到登录页。
- 临时活动页面跳转。
- 临时切换服务地址。

302 的语义是临时重定向，原 URL 通常仍然是主要资源地址。

实际客户端处理 302 时，可能将 POST 改为 GET。因此，如果必须保留原请求方法，需要考虑 307。

### 3. 303 See Other

表示客户端应当使用 GET 方法获取 `Location` 指定的另一个资源。对于 HEAD 请求，客户端使用 HEAD 获取目标资源。

常见场景是 POST/Redirect/GET（PRG）模式。

例如，用户提交表单后，服务器完成处理，再引导浏览器跳转到结果页面：

```http
HTTP/1.1 303 See Other
Location: /result
```

浏览器随后通过 GET 请求 `/result`，避免用户刷新页面时再次提交原表单。

### 4. 307 Temporary Redirect

表示临时重定向，并要求客户端在重定向时保留原请求方法和请求内容。

例如，客户端使用 POST 提交数据，服务器临时将请求转发到另一个地址：

```http
HTTP/1.1 307 Temporary Redirect
Location: /new-endpoint
```

客户端应当向新地址继续发送 POST 请求，并保留相应请求内容。

因此，当临时重定向时必须保留 POST 方法时，307 比 302 更合适。

### 5. 308 Permanent Redirect

表示永久重定向，同时要求客户端保留原请求方法。

它可以理解为与 301 相对应的、明确保留请求方法的永久重定向状态码。

### 6. 304 Not Modified

304 与其他常见的页面重定向不同，它主要用于协商缓存。

浏览器可能已经缓存了一份资源。当缓存需要重新验证时，浏览器可以向服务器发送条件请求，询问缓存是否仍然有效。

例如：

```http
GET /app.js HTTP/1.1
If-None-Match: "abc123"
```

如果服务器判断缓存对应的资源仍然有效，就可以返回：

```http
HTTP/1.1 304 Not Modified
ETag: "abc123"
```

浏览器此时可以继续使用本地缓存的资源，而不必重新下载完整内容。

304 响应不包含响应内容，客户端会根据缓存机制使用已有的响应数据。

常见的缓存验证字段包括：

- `If-None-Match`：根据实体标签 ETag 验证。
- `If-Modified-Since`：根据资源修改时间验证。
- `ETag`：标识特定版本的资源。
- `Last-Modified`：表示资源最近一次修改时间。

需要注意，304 不是错误，也不是普通页面跳转；它的主要作用是帮助客户端在缓存仍然有效时避免重复传输资源内容。

## 四、302、303、307 的区别

这三个状态码容易在面试中混淆。

| 状态码 | 重定向类型 | 对请求方法的处理 | 常见用途 |
|---|---|---|---|
| 302 Found | 临时 | 客户端可能将 POST 改为 GET | 临时跳转 |
| 303 See Other | 临时 | 后续获取目标资源时使用 GET；HEAD 请求继续使用 HEAD | 表单提交后跳转结果页 |
| 307 Temporary Redirect | 临时 | 保留原请求方法和请求内容 | 临时切换接口地址且需要保留 POST |
| 301 Moved Permanently | 永久 | 客户端可能将 POST 改为 GET | 永久迁移 URL |
| 308 Permanent Redirect | 永久 | 保留原请求方法和请求内容 | 永久迁移且需要保留 POST |

一个重要的历史背景是：302 在早期客户端实现中经常被处理为 POST 转 GET。为了更明确地区分不同语义，HTTP 后续定义了 303 和 307 等状态码。

因此，不能简单说“302 一定会把 POST 改成 GET”，也不能说“所有浏览器的行为完全一致”。实际处理应遵循相应 HTTP 规范和客户端实现。

## 五、4xx：客户端错误状态码

4xx 表示请求存在问题，或者客户端无法获得请求资源的访问权限。

### 1. 400 Bad Request

表示服务器认为客户端请求存在语法错误或其他无效内容，无法正常处理。

常见场景：

- 请求参数格式不正确。
- JSON 格式错误。
- 缺少必要参数或参数值不符合接口约定。

例如，后端要求接收 JSON，但前端提交的内容不是合法 JSON，服务器可能返回 400。

### 2. 401 Unauthorized

表示请求缺少有效的身份认证凭据，或者提供的认证凭据无效。

常见场景：

- 用户尚未登录。
- Token 缺失。
- Token 已过期或无效。

在 HTTP 认证语义中，401 响应通常需要包含 `WWW-Authenticate`，用于说明适用的认证方式或认证挑战。实际应用也经常将 401 用于表示登录状态失效。

前端可以根据接口约定，引导用户重新登录或刷新 Token。

### 3. 403 Forbidden

表示服务器理解请求，但拒绝授权访问该资源。

常见场景：

- 用户已登录，但没有管理员权限。
- 当前角色不能访问指定接口。
- 服务器访问控制策略禁止该操作。

401 和 403 的主要区别：

- **401：** 身份认证缺失或无效，需要解决认证问题。
- **403：** 服务器拒绝授权访问，即使用户已通过身份认证，也可能没有相应权限。

实际系统的错误处理可能有自己的约定，但这一区分是理解 HTTP 语义的基础。

### 4. 404 Not Found

表示服务器未找到请求的资源，或者不愿意明确告知请求资源是否存在。

常见场景：

- URL 路径写错。
- 资源已删除。
- 请求的业务记录不存在。
- 前端路由未正确配置，刷新页面时服务器找不到对应路径。

例如，前端请求 `/api/users/999`，如果该用户不存在，后端可以根据接口设计返回 404。

### 5. 405 Method Not Allowed

表示服务器识别请求使用的方法，但该资源不允许使用这种方法。

例如，某接口只允许 GET，而客户端使用 POST 请求，就可能返回 405。

服务器在返回 405 时，应通过 `Allow` 响应头列出该资源允许使用的方法，例如：

```http
HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD
```

注意：`Allow` 与 `Access-Control-Allow-Methods` 不同。前者描述资源允许使用的 HTTP 方法；后者用于 CORS 场景，说明跨源请求可以使用哪些方法。

### 6. 408 Request Timeout

表示服务器在等待客户端请求时，没有在规定时间内收到完整请求。

它与 504 不同：408 主要与接收客户端请求超时有关，而 504 表示网关或代理未能及时从上游获得响应。

### 7. 409 Conflict

表示请求与目标资源当前状态发生冲突。

例如：

- 创建用户时，用户名已被占用。
- 修改数据时，资源版本已经发生变化。

实际接口也可能使用 400 或 422 表达某些业务冲突，具体取决于 API 设计。

### 8. 422 Unprocessable Content

表示服务器理解请求内容的媒体类型，且请求内容语法有效，但无法处理其中的指令或数据。

常见场景是请求 JSON 格式正确，但字段不符合业务校验规则。

例如，邮箱格式无效或某个字段不满足约束时，API 可能返回 422。

### 9. 429 Too Many Requests

表示客户端在一定时间内发送了过多请求。

常见场景：

- API 请求频率超过限制。
- 登录尝试次数过多。
- 服务端实施接口限流。

服务器可以通过 `Retry-After` 告知客户端何时可以重试。

## 六、5xx：服务器错误状态码

5xx 表示服务器在处理请求或履行网关职责时遇到了问题。

### 1. 500 Internal Server Error

表示服务器遇到了意外情况，无法完成请求。

常见原因：

- 后端代码抛出未处理的异常。
- 数据库操作失败。
- 业务逻辑出现未预期的问题。
- 服务内部配置异常。

前端排查时，应查看接口响应、请求参数和后端日志，不能只凭 500 就认定是前端代码错误。

### 2. 501 Not Implemented

表示服务器不支持完成请求所需的功能。

例如，服务器不支持所请求的方法或某种功能。

它与 405 不同：405 表示服务器识别该方法，但当前资源不允许使用；501 表示服务器不支持完成该请求所需的功能。

### 3. 502 Bad Gateway

表示服务器作为网关或代理时，从上游服务器获得了无效响应。

常见场景：

- Nginx 代理的后端服务没有正常响应。
- 上游服务异常退出。
- 代理与后端之间的连接或协议出现问题。

排查时通常需要检查代理配置、上游服务状态、网络连通性和服务日志。

### 4. 503 Service Unavailable

表示服务器暂时无法处理请求，通常是因为过载、维护或其他临时不可用的情况。

常见场景：

- 服务正在维护。
- 服务过载，暂时无法接受更多请求。
- 系统主动拒绝请求以保护后端资源。

如果能够预估恢复时间，服务器可以通过 `Retry-After` 告知客户端建议的重试时间。

注意：Nginx 的限流、连接限制等具体配置可能返回不同状态码，取决于实际配置，不能认为所有限流都会返回 503。

### 5. 504 Gateway Timeout

表示服务器作为网关或代理时，未能及时从上游服务器获得响应。

常见场景：

- 后端接口执行时间过长。
- 上游服务响应超时。
- 代理服务器等待后端响应超过了配置的超时时间。

502 与 504 的区别：

- **502：** 上游返回了无效响应，或者代理无法将上游响应视为有效响应。
- **504：** 代理等待上游响应超时。

如果前端请求接口时出现 504，应进一步排查后端处理耗时、数据库查询、服务间调用以及代理超时配置。

## 七、如何理解状态码与前端开发的关系？

### 1. 状态码与 fetch 的关系

使用原生 `fetch` 时，收到 404、500 等 HTTP 错误响应，通常不会直接导致 Promise reject。

```js
async function getUser() {
  const response = await fetch('/api/user');

  if (!response.ok) {
    throw new Error(`HTTP error: ${response.status}`);
  }

  return response.json();
}
```

`fetch` 的 Promise 通常会在请求发生网络错误等情况下 reject。对于正常收到的 HTTP 错误响应，需要通过 `response.ok` 或 `response.status` 判断。

### 2. 状态码与 Axios 的关系

Axios 默认通常会将 2xx 以外的 HTTP 响应视为错误，并进入 `catch` 分支。

```js
try {
  const response = await axios.get('/api/user');
  console.log(response.data);
} catch (error) {
  if (error.response) {
    console.error('HTTP 状态码：', error.response.status);
  } else {
    console.error('请求未获得有效的 HTTP 响应：', error.message);
  }
}
```

其中：

- `error.response` 存在时，通常表示服务器返回了 HTTP 响应，但状态码未满足 Axios 的成功判定规则。
- `error.response` 不存在时，可能是网络错误、连接失败、超时等情况。

具体行为也会受到 Axios 配置和拦截器的影响。

### 3. 状态码与业务错误的区别

HTTP 状态码和业务错误码不是一回事。

例如：

```json
{
  "code": 10001,
  "message": "用户不存在",
  "data": null
}
```

这里的 `code` 是业务系统自定义的错误码，不是 HTTP 状态码。

服务器完全可能返回 HTTP 200，但响应体中的业务码表示失败。因此，前端需要同时理解 HTTP 层面的处理结果与业务层面的结果。

## 九、面试重点总结

### 1. 301 和 302 有什么区别？

301 表示永久重定向，302 表示临时重定向。客户端可能对 POST 请求进行 GET 转换，因此需要保留方法时应考虑 307 或 308。

### 2. 302、303、307 有什么区别？

302 是临时重定向，客户端可能将 POST 转换为 GET；303 明确要求使用 GET 获取目标资源（HEAD 请求除外）；307 要求保留原请求方法和请求内容。

### 3. 304 是重定向吗？

304 虽然属于 3xx，但主要用于协商缓存。服务器通过它告诉客户端缓存仍然有效，客户端可以继续使用已有的缓存响应内容。

### 4. 401 和 403 有什么区别？

401 表示缺少有效的身份认证凭据或认证失败；403 表示服务器拒绝授权访问，用户即使已经登录，也可能没有访问权限。

### 5. 502 和 504 有什么区别？

502 表示网关或代理获得了无效的上游响应；504 表示网关或代理未能及时获得上游响应。

### 6. 405 与 CORS 预检失败有什么区别？

405 是 HTTP 状态码，表示资源不允许使用当前请求方法。CORS 预检是浏览器跨源请求机制的一部分，浏览器会发送 OPTIONS 请求检查跨源访问策略。

如果服务器不支持该资源上的 OPTIONS 方法，可能返回 405；但 CORS 预检失败也可能是缺少或不匹配相关 `Access-Control-Allow-*` 响应头，并不一定返回 405。

## 十、总结

学习 HTTP 状态码时，不需要一开始就记住所有细分状态码。更重要的是掌握常见状态码的语义，以及它们在前端开发中的实际用途。

可以先记住以下规律：

- **2xx：** 请求成功处理。
- **3xx：** 需要进一步处理，重点理解重定向与缓存验证。
- **4xx：** 请求无效、认证失败或访问被拒绝。
- **5xx：** 服务器或网关处理请求时发生错误。

其中最值得优先掌握的是：

- 200、201、204、206。
- 301、302、303、304、307、308。
- 400、401、403、404、405、429。
- 500、502、503、504。

理解这些状态码的含义、触发场景和相互区别，就能应对大多数前端开发和 HTTP 面试中的相关问题。
