# 浏览器缓存：强缓存、协商缓存与缓存策略

## 一、什么是浏览器缓存？

浏览器缓存（Browser Cache）是指浏览器将请求获取的资源保存在本地，在后续访问时，根据缓存策略决定直接使用本地资源，还是向服务器验证资源是否发生变化。

常见的缓存资源包括：

- JavaScript 文件
- CSS 样式文件
- 图片、字体等静态资源
- HTML 文档
- 部分接口响应数据

例如，用户第一次访问网站时，浏览器需要下载 `app.js`、`style.css` 等资源。如果这些资源被缓存，用户再次访问时，就可能直接读取本地资源，而不需要重新下载。

浏览器缓存的主要作用有：

1. **提高页面加载速度**：减少资源下载所需的时间。
2. **减少网络请求**：在缓存有效时，可以直接使用本地资源。
3. **降低服务器压力**：减少重复的资源传输和处理。
4. **节省网络流量**：避免重复下载相同内容。

需要注意，浏览器缓存不意味着资源永远不会重新请求。浏览器会根据缓存响应头、资源类型、请求方式和用户操作等因素决定如何处理资源。

## 二、浏览器缓存的两种核心机制

HTTP 缓存主要分为两种机制：

- 强缓存（Freshness-based Caching）
- 协商缓存（Validation-based Caching）

两者的核心区别是：**强缓存命中时通常不需要向服务器发送请求；协商缓存需要向服务器验证资源是否发生变化。**

### 2.1 强缓存

强缓存是指浏览器判断本地缓存仍然有效时，直接使用缓存资源，不需要向服务器发送常规的网络请求。

强缓存主要通过以下两个响应头控制：

- `Cache-Control`
- `Expires`

#### 1. Expires

`Expires` 是 HTTP/1.0 引入的缓存字段，用于指定资源的绝对过期时间。

例如：

```http
Expires: Wed, 21 Oct 2026 12:00:00 GMT
```

在该时间之前，缓存通常可以直接使用；超过该时间后，浏览器需要根据其他缓存策略处理资源。

`Expires` 的问题在于，它依赖绝对时间。如果客户端与服务器的时间存在偏差，就可能影响缓存有效期的判断。

#### 2. Cache-Control

`Cache-Control` 是 HTTP/1.1 中重要的缓存控制字段，支持多种缓存指令。

例如：

```http
Cache-Control: public, max-age=3600
```

表示该响应可以被共享缓存存储，并在新鲜期内使用，缓存新鲜期为 3600 秒。

常见指令如下：

| 指令 | 含义 |
| --- | --- |
| `max-age=3600` | 响应在 3600 秒的新鲜期内可以使用 |
| `public` | 响应可以被私有缓存和共享缓存存储 |
| `private` | 响应只能由私有缓存存储，不允许共享缓存存储 |
| `no-cache` | 可以存储，但使用前需要进行验证 |
| `no-store` | 要求缓存不要存储该响应 |
| `s-maxage=3600` | 为共享缓存指定新鲜期，优先于 `max-age` |
| `max-stale` | 请求端允许接受一定程度上已经过期的响应，具体取决于指令及其参数 |

需要特别注意：

- `no-cache` 不等于不缓存，而是使用前需要验证。
- `no-store` 才是要求不存储响应。
- `private` 不代表资源绝对安全，只是限制共享缓存存储。
- `public` 不代表任何人都能绕过身份认证访问资源。
- `s-maxage` 主要用于 CDN 等共享缓存，不是普通浏览器私有缓存的替代品。

当 `Cache-Control` 和 `Expires` 同时存在时，通常优先使用 `Cache-Control` 中适用的缓存指令。

### 2.2 协商缓存

协商缓存是指浏览器在本地存在缓存资源的情况下，向服务器发送验证请求，由服务器判断资源是否发生变化。

如果资源没有变化，服务器返回 `304 Not Modified`，浏览器继续使用本地缓存的资源内容。

如果资源已经发生变化，服务器通常返回 `200 OK` 和新的资源内容。

协商缓存主要涉及两组请求头和响应头。

#### 1. Last-Modified 与 If-Modified-Since

服务器首次返回资源时，可以设置：

```http
Last-Modified: Tue, 20 Oct 2026 10:00:00 GMT
```

表示服务器认为该资源最后修改的时间。

浏览器再次验证资源时，会发送：

```http
If-Modified-Since: Tue, 20 Oct 2026 10:00:00 GMT
```

服务器将该时间与当前资源的修改时间进行比较。

- 如果资源没有发生可识别的修改，返回 `304 Not Modified`。
- 如果资源已经修改，返回 `200 OK` 和新的资源内容。

这种机制存在一些局限：

1. 时间通常只能精确到秒。
2. 同一秒内多次修改可能无法被准确识别。
3. 文件时间戳变化不一定意味着实际内容变化。
4. 部分部署或文件复制操作可能导致修改时间不够可靠。

#### 2. ETag 与 If-None-Match

`ETag` 是服务器为某个资源生成的验证标识，通常可以根据资源内容或服务器定义的版本规则生成。

例如：

```http
ETag: "abc123"
```

浏览器再次验证资源时，会发送：

```http
If-None-Match: "abc123"
```

服务器比较请求中的验证标识与当前资源的 ETag：

- 如果验证标识匹配，通常返回 `304 Not Modified`。
- 如果不匹配，返回 `200 OK` 和新的资源内容。

ETag 的优势是可以根据资源版本或内容生成标识，不必仅依赖修改时间。

但需要注意，ETag 不一定是内容哈希，也不一定在所有服务器之间相同。其生成规则由服务器决定。

#### 3. ETag 与 Last-Modified 的优先级

当两种验证方式同时存在时，HTTP 条件请求通常优先使用 `If-None-Match` 进行验证；如果请求中同时带有 `If-None-Match` 和 `If-Modified-Since`，服务器通常以 `If-None-Match` 为准。

实际应用中，服务器可以同时返回 `ETag` 和 `Last-Modified`，由浏览器在后续请求中使用相应的验证字段。

ETag 并非一定会增加服务器负担，也不能简单地认为负载均衡环境中不应使用 ETag。关键在于各服务器的验证标识是否与实际资源版本保持一致。

## 三、强缓存与协商缓存的区别

| 对比项 | 强缓存 | 协商缓存 |
| --- | --- | --- |
| 主要响应头 | `Cache-Control`、`Expires` | `ETag`、`Last-Modified` |
| 是否需要向服务器验证 | 缓存新鲜时不需要 | 需要 |
| 命中时的表现 | 直接使用本地缓存 | 通常返回 304，使用本地缓存内容 |
| 资源发生变化时 | 新鲜期内可能仍使用旧缓存 | 服务器发现资源变化后返回新内容 |
| 主要目的 | 避免重复请求 | 避免重复传输资源内容 |

这里的“命中”需要区分语境：

- 强缓存命中：直接使用有效的本地缓存。
- 协商缓存命中：服务器确认资源未变化，浏览器使用本地副本。

协商缓存返回 `304` 时，仍然发生了网络请求，只是服务器不需要重新传输完整的资源内容。

## 四、浏览器缓存的完整流程

假设浏览器请求一个 `app.js` 文件，服务器返回以下响应头：

```http
HTTP/1.1 200 OK
Cache-Control: max-age=3600
ETag: "v1"
Last-Modified: Tue, 20 Oct 2026 10:00:00 GMT
```

浏览器可以按照缓存策略存储资源及其相关元数据。

### 4.1 第一次请求

```text
浏览器
  |
  | GET /app.js
  v
服务器
  |
  | 200 OK + 资源内容 + 缓存响应头
  v
浏览器存储缓存
```

浏览器下载资源，并根据响应头判断是否可以缓存。

### 4.2 第二次请求：强缓存仍然有效

如果请求发生在资源的新鲜期内，且缓存适用于当前请求：

```text
浏览器检查本地缓存
        |
        v
缓存仍然新鲜
        |
        v
直接使用本地资源
```

通常不会向服务器发送该资源的常规 HTTP 请求。

在开发者工具中，这类资源可能显示为 `memory cache` 或 `disk cache`。

### 4.3 第三次请求：强缓存已经过期

当缓存变为不新鲜后，如果缓存中存在可用于验证的资源副本，浏览器可以向服务器发送条件请求。

例如：

```http
GET /app.js
If-None-Match: "v1"
If-Modified-Since: Tue, 20 Oct 2026 10:00:00 GMT
```

服务器检查资源版本。

**情况一：资源没有变化**

```http
HTTP/1.1 304 Not Modified
ETag: "v1"
```

浏览器继续使用本地缓存的资源内容。

**情况二：资源发生变化**

```http
HTTP/1.1 200 OK
Cache-Control: max-age=3600
ETag: "v2"
Content-Type: application/javascript

// 新版本的 JavaScript 内容
```

浏览器接收新的资源内容，并根据新的响应头更新缓存。

需要注意，缓存过期不意味着浏览器一定会发送条件请求。如果没有可用的缓存副本、缓存策略不允许存储，或者请求要求重新获取资源，浏览器可能直接发起普通请求。

## 五、为什么静态资源要添加版本号或哈希值？

在前端项目中，经常能看到这样的资源地址：

```text
/assets/app.8f31a2.js
/assets/style.91c7de.css
```

文件名中的哈希值通常与构建产物的内容或版本相关。

### 5.1 解决什么问题？

假设服务器部署了新的 `app.js`，但浏览器仍然缓存着旧版本。如果旧文件使用固定 URL，并且缓存时间很长，用户可能在缓存新鲜期内继续使用旧代码。

这可能造成：

- 页面功能没有更新。
- 新 HTML 引用了旧 JS。
- JS 与 CSS 版本不匹配。
- 页面出现运行错误。

### 5.2 使用内容哈希解决缓存更新问题

更常见的方式是构建时生成带内容哈希的文件名：

```text
旧版本：app.a1b2c3.js
新版本：app.d4e5f6.js
```

当文件内容变化时，构建工具生成新的文件名，HTML 引用新的 URL，浏览器就会把它作为新的资源处理。

这种方式称为缓存破坏（Cache Busting）。

通常可以采用以下策略：

- 带哈希的 JS、CSS：设置较长的缓存时间，并使用 `immutable`。
- HTML：设置较短的缓存时间，或者使用协商缓存。
- 用户个性化数据：根据隐私和业务需求设置缓存策略。

例如：

```http
Cache-Control: public, max-age=31536000, immutable
```

适合内容变化时会生成新 URL 的静态资源。

而 HTML 可以使用：

```http
Cache-Control: no-cache
```

这允许浏览器存储 HTML，但在使用前验证资源是否仍然有效。

这样既能利用静态资源的强缓存，也能及时发现 HTML 入口文件的变化。

## 六、浏览器刷新行为与缓存

面试中经常会问：点击刷新按钮、按 F5、按 Ctrl+F5 和在地址栏回车有什么区别？

可以先记住以下常见行为：

| 操作 | 常见缓存行为 |
| --- | --- |
| 普通导航或地址栏回车 | 按正常缓存策略处理 |
| 普通刷新或 F5 | 通常会重新验证部分资源，但具体行为由浏览器决定 |
| Ctrl+F5 或强制刷新 | 通常要求重新获取资源，并绕过或忽略部分本地缓存 |
| 开发者工具勾选 Disable cache | 开发者工具打开时，通常禁用相关 HTTP 缓存 |

需要注意，这些不是所有浏览器、所有版本都完全一致的硬性规则。浏览器可能对不同资源、导航类型和缓存状态采用不同策略。

普通刷新不一定每个资源都返回 `304`，强制刷新也不意味着所有浏览器实现都完全相同。

## 七、浏览器缓存的常见误区

### 7.1 误区一：304 表示没有网络请求

错误。

`304 Not Modified` 是服务器返回的 HTTP 响应，说明浏览器发送了验证请求，只是服务器没有重新传输完整的资源内容。

### 7.2 误区二：no-cache 表示不使用缓存

错误。

`no-cache` 允许缓存存储响应，但要求在使用前进行验证。`no-store` 才是要求缓存不要存储响应。

### 7.3 误区三：强缓存过期后一定使用协商缓存

不完全正确。

如果存在可用的缓存副本和验证器，浏览器可以使用协商缓存；如果没有可用副本，或者缓存策略不适用，浏览器可能直接重新获取资源。

### 7.4 误区四：ETag 一定是文件内容的哈希

错误。

ETag 是服务器定义的资源验证标识，可以由内容哈希、版本号或其他规则生成。

### 7.5 误区五：浏览器缓存只包括内存缓存和磁盘缓存

错误。

内存缓存和磁盘缓存是常见的本地缓存形式，但 HTTP 缓存体系还涉及共享缓存、Service Worker、Cache API 等机制。这些机制的行为和适用场景并不完全相同。

## 八、面试总结

浏览器缓存的核心是通过缓存策略减少重复的资源传输，提高页面性能。

需要重点掌握以下内容：

1. **强缓存**：由 `Cache-Control` 和 `Expires` 等字段控制。缓存新鲜时，通常不需要向服务器发起常规请求。
2. **协商缓存**：通过 `ETag`、`If-None-Match`、`Last-Modified` 和 `If-Modified-Since` 等字段验证资源是否变化。
3. **状态码**：`200` 通常表示返回了资源内容，`304` 表示资源未发生需要重新传输的变化，浏览器可以使用本地缓存副本。
4. **资源更新**：通过构建产物的内容哈希生成新 URL，避免用户长时间使用旧版静态资源。
5. **缓存设计**：带哈希的静态资源适合长时间缓存，HTML 入口文件通常需要更灵活的缓存策略。
6. **刷新行为**：普通刷新、强制刷新和正常导航的缓存行为可能不同，不能简单地认为每次刷新都一定返回 200 或 304。

真正理解浏览器缓存，关键不在于死记响应头，而是理解浏览器如何根据资源的新鲜程度、验证器和请求上下文，决定直接使用本地资源、向服务器验证，还是重新下载资源。
